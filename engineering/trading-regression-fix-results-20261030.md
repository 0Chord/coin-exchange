# Protobuf 경로의 성능 회귀 수정 결과

2026-10-30 · `test/http-trading-performance/142`

**Protobuf를 유지하며 큰 실행 함수의 컴파일 문제와 발생기의 불필요한 반복 작업을 수정했다.** 같은 동시 한도 256의 세 노드 비교에서 완료 TPS 중앙값은 31,687→34,375, 완료 p99는 51.22→42.22ms였다. 동시 한도 512를 별도로 시험하면 채택 코드의 완료 TPS 중앙값은 48,399였다. 아직 안정적인 50k TPS나 HTTP API의 성능으로 표현하지 않는다.

## 이번에 채택한 코드

기존 예약·정산 개선은 유지했다. 이번 추가 변경은 다음 세 파일이다.

| 파일 | 변경과 이유 |
|---|---|
| `domain-trading/.../TradingState.kt` | bounded 실행 함수에서 무체결 잔고 검증·체결 입력 구성·결과 관계 검증·수수료 합계 검증을 private 함수로 분리했다. `executePending` 바이트코드는 7,426→5,033바이트로 줄었다. 기존 JIT 로그의 C1 `out of virtual registers in linear scan` 실패가 최종 후보에서는 나타나지 않았다. |
| `app-api/src/test/.../HaTradingProbeClient.kt` | 완료 자료가 없을 때마다 잠금과 원자 카운터를 갱신하던 반복을 제거했다. 완료 자료가 생겼다는 표시는 기존 잠금 안에서 공개하며, drain과 다음 공개가 겹쳐도 자료를 놓치지 않는다. gate 상태가 그대로면 시간 조회도 반복하지 않는다. |
| `app-api/src/test/.../HaTradingProbeFlowTest.kt` | 빈 조회 뒤 새 완료 수신, drain과 동시 수신의 경합, gate 전환 시각·측정 창 끝의 대기 시간 합계를 검사한다. |

수수료·원장 합계·중복 ID·소유자·예약 hold·무체결 검사를 제거하지 않았다. 계산 오류와 실제 반영 중 오류의 분류, 반영 오류 뒤 상태 차단, observer의 시작·종료 경계도 유지했다. 발생기의 변경은 테스트 소스에 있으며 업무 상태나 운영 경로에 gate를 넣은 변경이 아니다.

## 같은 조건에서 수정 전후 비교

Mac M1 Pro 8코어·16GiB, 같은 Docker VM에 노드 세 개와 별도 발생기를 띄웠다. 각 컨테이너 CPU 2·메모리 2GiB·Heap 1GiB·G1, BTC/SOL/SUI partial-maker·공유 USDT·같은 수수료, Archive/catalog/Consensus sync=2, Driver `/dev/shm`을 유지했다. 세 노드가 동일한 입력을 복제하는 한 거래 클러스터이며 마켓별로 독립 확장된 클러스터의 수치는 아니다.

각 실행은 예열 20초 뒤 10초 제출한다. 실제 phase 시작부터 해당 cohort의 마지막 응답·완료 관측까지 TPS 분모에 포함한다. 발생기의 대기 시간을 빼거나 빠른 일부 응답만 고르지 않는다. 세 노드 완료에는 각 노드의 실제 완료 표식이 클라이언트에 도착하는 시간도 포함한다. HTTP와 별도 원격 Backup 저장 확인은 이 성능 경로에서 제외한다.

수정 전·후·후·전·전·후 순서로 여섯 번 실행했다. 아래 수치는 구성별 3회의 중앙값이며, 각 열의 중앙값이 반드시 같은 한 실행에서 나온 것은 아니다.

| 동시 접수 한도 256 | 접수 TPS | 접수 p95 / p99 (ms) | 세 노드 완료 TPS | 완료 p95 / p99 (ms) |
|---|---:|---:|---:|---:|
| 수정 전 | 31,702 | 14.80 / 27.48 | 31,687 | 30.46 / 51.22 |
| 채택한 수정 | 34,392 | 13.69 / 23.44 | 34,375 | 26.09 / 42.22 |

완료 TPS 중앙값은 약 8.5% 증가했다. 노드당 서비스 스레드 CPU/주문의 중앙값은 13.39→11.92μs, 할당은 11,596→11,241B였다. CPU·할당은 노드별 전후 checkpoint 차분을 세 노드 평균한 뒤 실행별 중앙값을 냈다. 종료 CAPTURE와 경계 제어 비용이 포함되며 순수 매칭 CPU나 전체 서버 CPU를 뜻하지 않는다.

| 비교 쌍 | 수정 전 완료 TPS | 수정 후 완료 TPS | 수정 전 / 후 완료 p99 (ms) |
|---|---:|---:|---:|
| 1 | 32,960 | 37,917 | 51.22 / 31.92 |
| 2 | 17,399 | 34,375 | 167.43 / 42.22 |
| 3 | 31,687 | 29,878 | 40.99 / 45.08 |

**마지막 쌍은 수정 후 더 느렸다.** 느린 기준선과 불리한 결과를 모두 보존했다. 모든 실행에서 같은 향상률이 재현됐거나 역사적 하락의 전부가 해결됐다고 주장하지 않는다. 이 비교는 도메인 수정과 발생기 수정의 합계 효과다.

## 동시 한도 512의 별도 결과

256 한도가 가득 찬 시간이 제출 창의 약 95%여서 발생기가 더 못 보내는 영향을 확인했다. 채택 코드를 바꾸지 않고 512와 1,024를 한 번씩 시험한 뒤, 아래 Map 후보 비교에서도 **동일한 512 조건으로 채택 코드 3회**를 확보했다.

| 채택 코드·한도 512 | 접수 TPS | 완료 TPS | 완료 p95 / p99 (ms) |
|---|---:|---:|---:|
| 1 | 37,954 | 37,935 | 46.53 / 93.15 |
| 2 | 48,434 | 48,399 | 32.93 / 47.45 |
| 3 | 50,137 | 50,103 | 30.58 / 43.98 |
| 중앙값 | 48,434 | 48,399 | 32.93 / 47.45 |

접수 p95/p99 중앙값은 16.91/26.44ms이며 최종 ACK까지 포함한 cohort TPS 중앙값은 48,398이다. 한도 확대는 코드 개선 효과와 구분한다. 기본 한도 256을 자동 변경하지 않았다. 512에서 단회 5만을 넘었지만 최소 실행은 약 3.79만이었다. 1,024 단회 시험은 약 4.82만 TPS·완료 p99 53.20ms로, 추가 처리량에 비해 tail이 나아지지 않았다. 위 수치는 단기 관측 처리량이며 엔진의 절대 최대 지속 용량은 확정하지 못했다.

## 새 JVM의 엔진 단독 회귀

기존 프로브를 그대로 사용해 새 JVM마다 1,000건 예열·5,000건 측정을 같은 순서로 세 쌍 실행했다. SELL 준비 6,000건 뒤 BUY 접수→매칭·정산→ACK까지 처리한다. 전송과 HTTP는 제외한다.

| 3회 중앙값 | 수정 전 | 채택한 수정 |
|---|---:|---:|
| TPS | 34,075 | 59,351 |
| p95 / p99 (μs) | 36.29 / 83.29 | 22.00 / 63.00 |
| CPU / 주문 (μs) | 29.10 | 16.75 |
| 할당 / 주문 (B) | 11,474 | 11,410 |

세 쌍 모두 TPS·CPU가 개선됐다. 다만 JIT의 영향을 크게 받는 짧은 프로세스 시작 구간이다. 59,351을 지속 최대 TPS나 세 노드 TPS로 확대하지 않는다. 중간 후보는 함수를 덜 분리해 결과가 혼재했으며 `engine-paired.json`에 남겼다. 최종 후보의 컴파일 로그와 별도로 구분한다.

## Map 축소 후보는 시험 후 제외

두 예약·최대 네 잔고의 작은 단일 체결 입력에서는 Map 두 개를 만들지 않고 직접 조회하는 후보도 구현했다. 큰 입력·추가 입력·중복 입력은 기존 경로로 처리했고 독립 코드 검토와 도메인 회귀를 통과했다.

같은 엔진 프로브의 새 세 쌍에서는 CPU·할당·TPS가 모두 개선됐다. 그러나 다른 것은 그대로 두고 도메인 JAR만 바꾼 세 노드·한도 512 비교에서는 아래처럼 결과가 혼재했다.

| 3회 중앙값·한도 512 | 채택 코드 | Map 축소 후보 |
|---|---:|---:|
| 완료 TPS | 48,399 | 45,049 |
| 완료 p95 / p99 (ms) | 32.93 / 47.45 | 37.59 / 50.96 |
| 노드 CPU / 주문 (μs) | 10.34 | 11.39 |
| 노드 할당 / 주문 (B) | 11,263 | 10,509 |

세 쌍의 완료 TPS 변화는 −4.6% / +8.8% / −10.1%였다. 감소 원인을 코드로 확정할 만큼 편차를 통제하지 못했으나 전체 경로의 이득을 입증하지도 못했다. **할당이 줄었다는 이유만으로 채택하지 않았다.** 후보 두 파일을 검증된 이전 상태로 복원했으며 후보·패치·결과는 보존했다. 단회 52,638 TPS를 현재 코드의 성과로 인용하지 않는다.

## 이전 3.5만→2.6만은 원인이 밝혀졌나

아직 전부를 확정하지 못했다. 보존된 옛 실행물을 이번에 다시 실행하면 완료 36,926 TPS, 수정 전 현재 실행물은 36,400 TPS였다. 이 네 구성의 탐색은 각 1회이므로 정량적인 원인 기여율을 계산하지 않는다. 과거 하락은 이번에 일관되게 재현되지 않았다.

별도로 확인한 실제 비용은 두 가지다. 기존 발생기는 10초 창에서 수천만 번 빈 완료 확인의 잠금·원자 카운터 경로를 지났고, 큰 실행 함수에는 초기 C1 컴파일 실패가 있었다. 수정 후 collector의 표본으로 추정한 잠금 횟수/주문은 약 204→4.83으로 감소했다. 새 표본은 빈 조회를 제외하므로 이전 평균 잠금 대기와 단순 비율로 CPU 감소를 계산하지 않는다. 원자 카운터·JIT 문제를 고친 사실을 과거 하락분 전체의 단일 원인으로 확대하지 않는다.

위 장애 시험은 같은 Mac에서 독립 JVM으로 실행했다. 물리적으로 다른 AZ·스토리지의 전원 장애를 실증한 시험은 아니다. LOCAL_QUORUM 성능을 원격 저장 확인까지 포함한 성능으로 취급하지 않는다.

이번 부하는 매 실행 고유 컨테이너·볼륨을 정리했다. 기존 2GiB 기록 cap·1.75GiB 조기 종료·호스트 8GiB 여유 기준을 유지했다. 원본 요약·소스 지문·작은 컴파일 로그를 남기며 대용량 실험 기록은 누적하지 않았다.

## 남은 범위와 근거

- SBE는 계속 제외한다. 기존 Protobuf schema87/version3과 Snapshot 형식2를 유지한다.
- Map 축소는 시험 후 기각했다. P4 매칭 참조 축소·scratchpad·한 입력으로 접수/실행 통합·클러스터 분리까지 모두 구현했다는 상태가 아니다.
- 최신 HTTP API 성능과 원격 Backup 보호 profile의 성능은 이번에 측정하지 않았다. 새 코드를 기반으로 단기 기본 경로 개선을 검증한 기록이다.
- 50k 지속 처리와 모든 tail 원인의 확정은 남았다. 잠금 제거·컴파일 수정이 실측 개선으로 이어진 범위까지만 기록한다.

실행 근거는 [결과 폴더](results/regression-fix-20261030/)에 보존한다. 주요 원본은 `cluster-paired.json`·`engine-final-paired.json`·`map-cluster-paired.json`, 지문은 `source-v2-manifest.json`·`after-runtime.json`·`final-image-identities.json`이다. 검토 결과는 `code-independent-review.md`와 `measurement-independent-review.md`, 검증 결과는 `validation-summary.json`을 확인한다. [이전 SBE 비교 기록](trading-optimization-results-20261030.md)은 당시의 결과로 유지한다.
