# 엔진의 첫 자금을 한 번만 준비하기 · #95

**이 문서는 [#95](https://github.com/0Chord/coin-exchange/issues/95)의 명세다.** 초기 자금 기능 하나를 구현한다. #88은 실제 통신·접수·기록 검증을 추적하는 별도 묶음이다. [다섯 작업의 순서](aeron-admission-plan.md)에서 전체 연결을 볼 수 있다.

**이번에 만들 결과:** 주문 테스트에 사용할 초기 잔고를 준비한다. 사용자에게 테스트용 자금을 한 번 지급하고, 지급 기록을 남긴다. 같은 요청을 다시 보내도 돈이 늘어나지 않는다. 지급한 잔고를 기존 주문 접수에서 그대로 사용한다.

**상태:** 2026-10-17 구현 요청에 따라 로컬 구현·필수 검사·독립 리뷰를 완료했다. PR·CI·병합의 최신 상태는 GitHub에서 별도로 확인한다. 같은 준비 ID·같은 사용자·자산·금액은 최초 결과를 재사용하고, 내용이 달라지면 충돌이다. [실제 흐름·테스트 설명·검증 기록](engine-opening-balance.md)을 함께 읽는다. 아래 설계 당시 미실행 표시는 당시 기록이며 현재 실행 상태는 구현 기록을 기준으로 한다.

| 구분 | 하는 일 |
| --- | --- |
| 지금 보는 문서 | 통신 없이 접수 엔진의 메모리에 최초 자금과 OPENING 원장을 한 번 준비한다. |
| 기존 #88 | 실제 Aeron 통신·실행·로그 검증 묶음이다. #97·#98·#99로 나누어 등록했다. |

예시는 **사용자 A에게 1,000 USDT 준비 → 300 USDT 주문 예약 → 같은 준비 요청 재전송**이다. 결과는 사용 가능 **700 USDT**, 예약 **300 USDT**를 유지한다. 다시 1,000 USDT로 덮어쓰거나 1,000 USDT를 추가 지급하지 않는다.

금액을 준비한 근거는 OPENING, 그 돈을 주문에 묶은 근거는 RESERVE다. 이번 준비는 주문 승인 순번·대기 주문·주문 요청 이력을 만들지 않는다.

## 확인한 사실

기준은 #94가 머지된 통합 커밋 `9d33ee36e7f36ff24764dfd83f5bba7639364792`다.

- [`OpeningBalance`](../domain-ledger/src/main/kotlin/com/exchange/core/ledger/OpeningBalance.kt)는 준비 ID·사용자·자산·양수 금액을 검증하고, OPENING 분개와 이력 없는 영 잔고의 개시 조건을 제공한다. `OpeningBalanceResult`도 이 파일에 있다.
- [`OrderAdmissionState`](../domain-trading/src/main/kotlin/com/exchange/core/trading/OrderAdmissionState.kt)는 현재 사용자·자산 잔고, 예약 근거·대기 주문, 원장 ID 사용 이력과 요청 최초 결과를 소유한다. 생성자 초기 잔고는 있지만 명시적인 개발 자금 준비 입구는 없다.
- [`PostgresDevelopmentBalanceStore`](../app-api/src/main/kotlin/com/exchange/core/api/ledger/infrastructure/persistence/PostgresDevelopmentBalanceStore.kt)는 DB 트랜잭션과 행 잠금을 사용하며 ID·현재 시각을 내부에서 만든다. 이 저장 구현을 메모리 엔진에 연결하지 않는다.
- [#88](https://github.com/0Chord/coin-exchange/issues/88)은 자금이 같은 실행 경로의 확정 입력으로 준비될 것을 요구한다. 이번 순수 코어 선행만 완료했다고 실제 전송·확정 기록까지 준비됐다고 표시하지 않는다.

## 책임·배치 제안

`domain-trading`의 기존 `OrderAdmissionState`에 개발용 최초 자금 준비 동작 하나를 추가한다. 이름 제안은 `prepareDevelopmentBalance`다. 입력은 기존 `OpeningBalance`와 호출자가 정해 전달한 `ledgerTransactionId`·`occurredAt`, 성공 결과는 기존 `OpeningBalanceResult`를 재사용한다. 준비 원본과 실제 생성한 OPENING 원장도 불변 관찰 기록으로 남긴다. 정확한 내부 자료구조와 관찰 필드 이름은 구현자가 조정할 수 있다.

새 Balance 저장소·별도 자금 상태 객체·포트·모듈을 추가하지 않는다. `OpeningBalance.requireUnused`, `OpeningBalance.transaction`, `Balance.credit`를 사용하고 개시 분개나 금액 계산을 새 공식으로 복제하지 않는다. 기존 constructor와 주문 API를 유지한다.

엔진 안에서 현재 시각이나 무작위 ID를 만들지 않는다. DB 코드의 마이크로초 절삭도 옮기지 않고 전달받은 Instant를 보존한다. 새 개시에 사용할 원장 ID는 현재 접수와 같은 검증을 재사용한다. 입력 문자는 기존 OpeningBalance 계약을 따르며, 아직 없는 전송 코덱의 UTF-8 길이 보장을 이번 코어가 제공한다고 쓰지 않는다.

## 포함·제외

포함은 단일 사용자·자산의 최초 준비, 중복/충돌 판단, 실제 OPENING·잔고의 메모리 반영, 주문 접수와의 이력 공유, 관찰 결과 보호와 관련 상태 테스트다. 금액 단위는 기존 Amount의 최소 단위 정수다.

Protobuf 변경, Aeron 드라이버·확정 콜백·복제·Archive·스냅샷·재시작 복구, DB 읽기·복사·마이그레이션, HTTP·CLI·자동 시작 훅, 여러 계정 묶음의 일괄 원자성, 추가 입금·충전, 마켓·수수료 등록은 제외한다. 이번 준비를 호출했다고 기존 SQL 자금과 엔진 자금을 함께 지출할 수 있는 것은 아니다.

## 새 준비와 반복 준비

1. **상태 차단 확인:** 기존 #85·86 계약처럼 차단된 객체는 신규 준비뿐 아니라 과거 준비 재전송도 거절한다.
2. **원본 대조:** 준비 ID는 이 상태 객체 수명 안에서 전체 사용자·자산을 통틀어 한 원본을 가리킨다. 사용자별 요청 ID로 좁히지 않는다. 기존 `OPENING:<preparationId>`의 의미를 유지한다. 프로세스 재시작이나 다른 클러스터까지 중복을 막는 보장은 이번에 추가하지 않는다.
3. **이미 같은 ID가 있으면:** 사용자·자산·금액이 같을 때 최초 준비 원본·원장 ID·시각을 재사용한다. 현재 잔고를 최초 금액으로 되돌리지 않는다. 값이 다르면 `OpeningBalanceRequestConflictException`으로 끝낸다. 동일 원본 재전송에서 새로 받은 원장 ID·시각 문맥은 사용하지 않는다.
4. **새 ID라면:** 대상 잔고가 없거나 자금 이력 없는 영 잔고여야 한다. 다른 ID로 이미 개시·사용한 계정을 다시 지급하면 `OpeningBalanceConflictException`이다. 초기 constructor의 비영 잔고도 새 개시 대상이 아니다. 없는 계정은 계산용 0 잔고로 보고 성공 전에는 새 항목을 만들지 않는다.
5. **반영 구간에 들어가기 전에 계산·검증:** 기존 규칙으로 다음 잔고와 OPENING 두 분개를 만들고, 최초 결과를 준비한다. 개시와 예약이 원장 거래 ID·사건 ID 사용 이력을 공유한다. OPENING과 RESERVE 어느 쪽이 먼저였든 같은 원장 ID를 다시 쓰지 않는다.
6. **한 실행자가 순서대로 반영:** 잔고, 개시 원본/결과/원장, 사용 이력을 같은 소유 객체에 기록한다. 주문 승인 순번·대기 주문·주문 요청 기록은 바꾸지 않는다. 정상 반영이 끝난 뒤 준비 결과를 돌려준다.

기존 결과 타입의 `alreadyPrepared`는 최초 false·재호출 true로 표시한다. 같게 유지할 것은 최초 준비 원본·원장 ID·시각이며, 저장된 최초 결과는 수정하지 않는다. 이 결과는 현재 잔고 조회 응답이 아니다. 무작위 ID 생성이나 시각 조회를 엔진 안에 추가하지 않는다.

## 무엇을 자금 사용 이력으로 볼까

이미 남긴 개시 원장, 승인된 주문의 해당 자산 예약·원장과 기존 비영 초기 계정의 근거는 유지한다. 잔고가 나중에 0이 되어도 사용 이력을 잊고 다시 개시하지 않는다. 현재 객체가 가진 근거만 판단하며, 과거 DB의 이력이나 재시작 전 상태를 알아낸다고 약속하지 않는다.

**부족 거절 기록 자체는 자금을 쓴 이력이 아니다.** 빈 상태의 주문 R1이 부족으로 거절된 뒤 최초 개시는 허용할 수 있다. 그 후 같은 R1은 #86대로 첫 부족 거절을 돌려주고, 새 요청 R2만 최신 잔고로 판단한다. 요청 기록이 있다는 이유만으로 최초 개시를 막지 않는다.

## 합의한 숫자와 상태 기대값 · 실제 검증은 구현 기록에 연결

표의 표시 단위는 USDT다. 테스트의 Amount는 기존 최소 단위 정수로 적는다. 예를 들어 시연 USDT 1개를 1,000,000단위로 정하면 1,000 USDT는 `Amount(1_000_000_000)`다. BUY 3 BTC × 100 USDT 사례는 BTC scale 8, 수량 `300_000_000`, 가격 `100_000_000`, 수수료 0으로 예약 `300_000_000`단위가 된다. 이는 고정 테스트 문맥이며 운영 자산 정책을 확정하는 값이 아니다.

| 상황·실행 | 기대 결과·관측 |
| --- | --- |
| 빈 상태에 P1/A/USDT/1,000, 원장 L1·시각 T1 | 사용 가능 1,000 USDT·예약 0, OPENING 한 건과 두 분개. 준비 기록 1, 주문 순번 0·대기/요청 없음 |
| 같은 P1·같은 원본 재호출 | 최초 L1/T1 유지, alreadyPrepared=true. 잔고·원장·저장된 최초 기록에 추가 효과 없음 |
| 최초 준비 → BUY 300 USDT 예약 → 같은 P1 재호출 | 사용 가능 700 USDT·예약 300 USDT 유지. 최초 개시 원본 1,000 USDT·L1/T1과 예약 원장 한 건이 각각 유지 |
| P1의 금액·사용자·자산을 각각 바꿔 재호출 | 요청 내용 충돌. 두 사용자/자산의 현재 상태와 모든 원장·기록 유지 |
| 새 P2로 이미 개시한 같은 A/USDT에 준비 | 추가 개시 충돌. 개시 원장·금액은 한 번만 유지 |
| 서로 다른 준비 ID로 다른 사용자 또는 다른 자산 준비 | 각각 독립적으로 개시. 같은 준비 ID를 다른 계정에 재사용하면 충돌 |
| 초기 constructor에 명시한 0 잔고 / 비영 잔고 | 이력 없는 0은 최초 개시 가능. 비영 잔고는 추가 개시 거절하며 과거 OPENING을 소급 생성하지 않음 |
| 잔고 0에서 300 USDT가 필요한 R1 부족 거절 → P1로 1,000 USDT 준비 → R1 재전송 → 새 R2 | P1 가능. R1은 최초의 현재 0·필요 300·부족 300 USDT를 유지. R2는 승인되어 현재 사용 가능 700 USDT·예약 300 USDT. 준비가 기존 요청 이력을 지우지 않음 |
| 개시 L1 후 주문에서 L1 재사용 / 예약 L2 후 다른 계정 개시에 L2 재사용 | 양방향 원장 ID 충돌, 쓰기 전 상태 유지·계속 사용 가능 |
| 같은 원본 재전송에 다른 원장 문맥 전달 | 최초 원장 ID·시각을 사용하고 새 문맥을 소비하지 않음 |
| 금액 0·잘못된 준비 입력 또는 새 개시의 잘못된 원장 ID | 기존 도메인 검증과 동일하게 반영 전 오류. 상태·차단 여부 유지 |
| 미사용 계정에 최소 단위 1 / Long.MAX_VALUE 준비 | 기존 Amount 범위의 정확한 금액·두 분개. float·축약·넘침 보정 없음 |
| 각 실제 상태 쓰기 전후의 Exception·Error | 부분 반영 롤백을 가정하지 않고 원래 오류·차단 확인. 이후 신규/반복 준비·주문·정상 조회 거절 |
| 반환된 준비 목록을 수정하거나 이후 준비·주문 실행 | 내부 기록을 외부에서 바꾸지 못하며 이미 반환된 관찰값도 바뀌지 않음 |

OPENING은 기존 `OpeningBalance.transaction`의 `SYSTEM:<asset>:DEVELOPMENT_FUNDING` 차변과 사용자 AVAILABLE 대변을 그대로 사용한다. 이 사례에서는 두 항목이 각각 1,000 USDT이며 사용자 HOLD에 개시 분개를 넣지 않는다. 총합만 같다고 계정·자산·방향·유형·원본 ID·시각 검증을 생략하지 않는다.

정상·충돌·반영 전 실패는 실제 snapshot의 금액·준비 원본·OPENING/RESERVE·순번·대기·요청 기록을 대조한다. 실패 주입은 기존 상태 테스트의 방식으로 관측하고 제품에 테스트 전용 실패 스위치를 추가하지 않는다. 차단 뒤에는 정상 snapshot을 호출해 잔고가 되돌아왔다고 주장하지 않는다. DB·Aeron·가짜 거래 계산기로 이 순수 상태 검증을 대신하지 않는다.
