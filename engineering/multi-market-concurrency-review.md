# BTC와 SUI 주문이 동시에 와도 같은 USDT를 두 번 쓰지 않는다

**이번 #117은 1,000 USDT로 600 USDT짜리 BTC 주문과 500 USDT짜리 SUI 주문을 함께 보냈을 때, 하나만 승인되는지 검사한다.** 자금 엔진의 계산 방식은 바꾸지 않고, 기존 코드가 실제 세 노드에서 이 규칙을 지키는지 확인하는 테스트를 추가한다.

이전 #116은 BTC 응답을 받은 뒤 SUI를 보냈다. 이번에는 서로 다른 두 주문 클라이언트가 준비된 뒤 출발 신호를 함께 받는다. 실제 엔진에서는 Aeron이 정한 입력 순서대로 처리한다.

```text
PostgreSQL: BTC·SUI 설정 준비
  → 세 노드가 같은 버전과 내용을 읽었는지 확인
  → 사용자 U1에게 개발용 1,000 USDT 준비
  → 클라이언트 A: BTC 600 요청 ┐
     클라이언트 B: SUI 500 요청 ┴ 공통 GO → Aeron 클러스터
  → 실제 처리 위치로 먼저 처리된 요청 확인
  → 두 응답과 세 노드의 잔고·예약·최초 결과·원장 대조
  → 종료 후 전체 기록을 다시 검사하고 컨테이너·DB 정리
```

| 실제 처리 순서 | 승인 | 부족으로 거절 | 최종 사용 가능 USDT | 최종 예약 USDT |
| --- | --- | --- | ---: | ---: |
| BTC 먼저 | BTC 600 | SUI: 500 필요, 400만 남음 | 400 | 600 |
| SUI 먼저 | SUI 500 | BTC: 600 필요, 500만 남음 | 500 | 500 |

어느 경우든 승인 순번은 1, 대기 주문은 1건, 최초 요청 결과는 승인·거절 각 1건이다. 원장은 자금 준비 OPENING 1건과 승인 주문의 RESERVE 1건만 남는다. 체결·정산은 이번 검사에 포함되지 않는다.

<details markdown="1">
<summary>1. 두 클라이언트와 세 노드가 각각 무엇을 하는가</summary>

테스트 JVM은 Docker 실행과 결과 검사를 담당한다. 주문 클라이언트 A와 B는 별도 컨테이너/JVM에서 주문을 실제로 보낸다. 노드 0·1·2 역시 별도 컨테이너/JVM이며 각자 같은 자금 상태의 사본을 가진다. 세 노드 중 하나가 BTC만 맡고 다른 하나가 SUI를 맡는 구조가 아니다.

DB는 마켓 설정을 보관한다. 세 노드와 클라이언트는 시작할 때 지정 버전 V를 읽고, 등록 전 원문의 SHA-256 H와 비교한다. 주문 처리 시 쓸 돈은 각 노드의 `OrderAdmissionState` 안에 있다. BTC와 SUI 모두 `사용자 U1 + 자산 USDT`라는 같은 잔고를 선택한다.

GO는 테스트가 두 클라이언트를 함께 출발시키는 파일이다. 제품 코드의 잠금이나 동시성 제어 장치가 아니다. 각 클라이언트의 실제 연결·마켓·세션·컨테이너 격리를 확인한 뒤 딱 한 번 공개한다. A의 응답을 기다린 뒤 B를 시작하지 않는다.

A는 BTC 6개 × 100 USDT, B는 SUI 25개 × 20 USDT를 보낸다. BTC 수량 소수는 8자리, SUI는 9자리, USDT는 6자리다. 따라서 B의 **수량 원시값 25,000,000,000**과 **예약 금액 원시값 500,000,000**은 서로 다르다. 테스트의 사전 정답에서도 수량과 금액을 분리했다.

</details>

<details markdown="1">
<summary>2. 처리 순서와 응답 도착 순서가 다른 이유</summary>

예를 들어 엔진이 BTC를 먼저 승인하고 SUI를 뒤에 거절했어도, 두 클라이언트 연결의 수신 대기가 다르면 SUI 거절 응답을 먼저 볼 수 있다. 입력에 적힌 시각도 처리 순서를 정하지 않는다.

그래서 비교기는 응답의 승인 여부를 보고 승자를 고르지 않는다. 노드가 실제로 적용한 두 입력의 `cluster.logPosition()`을 찾는다. P1의 위치를 L0라 할 때 그 뒤의 서로 다른 위치 L1·L2가 필요하다. 더 작은 위치의 요청 ID로 위 표의 정답을 고른 뒤, 각 응답을 RA/RB로 찾아 비교한다.

- BTC가 L1이면 사용 가능 400·예약 600이 정답이다.
- SUI가 L1이면 사용 가능 500·예약 500이 정답이다.
- 승인 순번 1은 업무상 승인된 주문 번호다. 입력 로그 위치 L1과 같은 숫자가 아니다.

세 노드가 똑같이 틀려도 통과하면 안 된다. 노드 0의 결과를 정답으로 복사하지 않고, 미리 정한 잔고·예약·정책·최초 결과·원장의 모든 의미 값을 각각 비교한다.

종료 후에는 P1·A·B 세 입력의 고정 위치로 전체 적용 기록을 다시 검사한다. 계획 밖 요청이 끼거나 같은 요청이 다른 위치에서 다시 처리됐다면 실패한다. 같은 위치에서 응답 전송 상태만 갱신된 진단 행은 업무값이 그대로일 때 허용한다.

</details>

<details markdown="1">
<summary>3. 문제가 생기면 무엇이 실패하는가</summary>

| 상황 | 검사 결과와 의미 |
| --- | --- |
| 설정 버전·내용 불일치, SUI 누락, B가 BTC로 준비됨 | 준비 실패. 주문 쌍의 GO를 열지 않는다. P1은 이미 준비됐을 수 있다. |
| 출발 후 응답·적용 위치·세 사본 중 일부 누락 | 검증 불가. 돈이 안 움직였다고 단정하거나 자동 재전송하지 않는다. |
| 두 주문 모두 승인, 잘못된 잔고·정책·원장 | 불일치. 잘못된 위치와 필드를 보고서에 남긴다. |
| 마지막 출력 수집이나 정리 실패 | 앞서 발견한 불일치를 유지하면서 수집·정리 오류도 남긴다. |

기존 기한은 유지한다. 노드 준비 60초, 클라이언트 READY 90초, 각 컨테이너 확인 5초, GO 대기 120초, 출발 후 두 결과 수집 공통 20초, 세 사본 확인 15초다. 이 시간은 테스트의 대기 한도이며 실제 업무 순서를 정하는 시각이 아니다.

DB 비밀번호는 보고서에 남기지 않는다. 기존 제한된 Docker inspect와 전체 보고서 비밀번호 검사를 새 동시 경로에서도 사용한다. 컨테이너와 DB는 정리하되 Archive 기록은 기존 방식으로 보존한다.

</details>

### 이번 실제 실행에서 관측한 결과

새 사례 `CONCURRENT_MULTI_MARKET_SHARED_FUNDS`에서는 **SUI가 먼저 처리됐다.** 아래 위치는 이 실행에서 관측한 값이며 코드의 고정 기대값이 아니다.

| 실제 적용 위치 | 입력·결과 | 사용 가능 USDT | 예약 USDT |
| ---: | --- | ---: | ---: |
| 352 | P1 자금 준비 | 1,000 | 0 |
| 960 | B / RB / SUI / OB 승인, 승인 순번 1 | 500 | 500 |
| 1,152 | A / RA / BTC / OA 거절, 필요 600·현재 500·부족 100 | 500 | 500 |

세 노드 모두 같은 결과였고 마지막 대기 주문 1건·최초 요청 결과 2건·원장 2건을 확인했다. 실제 입력 시각은 A가 B보다 앞서지만, 적용 순서는 B가 먼저였다. 이 사례에서 응답 도착 시각의 역전을 측정했다고 주장하지 않는다.

마켓 설정은 버전 1, 원문 SHA-256 `ad7f03a451841c9d62d0e98581ea7aeff35b1b310e44d23c72404473d50baa3a`였다. 종료 후 세 checkpoint 전체 대조 오류 0, 정상 종료 확인, DB·네트워크 정리 오류 0이다.

전체 컨테이너 10개 사례가 모두 통과했다. 새 사례는 실제 Docker를 한 번 실행했으며, BTC가 먼저인 반대 순서는 빠른 독립 관찰 자료로 확인했다. 기존 BTC/BTC 동시 사례에서는 A가 먼저였지만 이를 BTC/SUI의 반대 순서를 실제 실행한 근거로 세지 않는다.

새 사례의 원본 보고서는 작업 폴더 아래 `app-api/build/reports/aeron-funding/funding179266427988372540cce/result.json`에 있다. `steps`, `concurrentPositions`, `concurrentClientEvents`, `observations`, `issues`, `cleanStop`에 입력부터 최종 정리까지 연결돼 있다.
