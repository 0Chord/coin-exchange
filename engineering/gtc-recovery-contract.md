# LIMIT/GTC 접수와 복구 계약 — #43

> **설계 계약 · 제품 구현 전.** [#43](https://github.com/0Chord/coin-exchange/issues/43)의 산출물이다. 접수한 주문을 서버 종료 뒤 이어 처리하기 위한 기록과 순서를 정한다. 복구·원장 기능은 아래 후속 이슈에서 구현한다.

먼저 네 가지 결정 → 한 주문의 흐름 → 중단 사례를 읽는다. 저장할 필드·중복 방지·수용 예시·현재 코드 근거는 상세 절에서 펼친다.

## 먼저 볼 결정 네 가지

| 결정 | 현재 상태 |
| --- | --- |
| 언제 접수한 주문인가 | **합의:** 주문 입력·자금 예약을 같은 DB 트랜잭션으로 저장한 시점. 이후 중단은 이어 처리한다. HTTP 성공 응답은 별개다. |
| 어떤 기록으로 복구하나 | **합의:** 확정된 매칭 결과로 주문장을 복원하고, 접수 기록만 남은 요청만 실행한다. 과거 전체 주문을 다시 매칭하지 않는다. |
| 어떤 환경에서 검증하나 | **수정 합의:** 현재 형식의 개발 데이터를 준비하고, 서버를 재시작할 때 같은 DB를 유지한다. 새 DB 생성이나 구형 DB 전용 판별·차단 기능은 요구하지 않는다. |
| 잔고를 무엇으로 설명하나 | **추가 합의:** 초기 자금·예약·취소 반환까지 원장에 기록하고 available/hold와 대조한다. 불일치를 자동 덮어쓰기로 감추지 않는다. |

아래는 **접수 확정·복원 방식·개발 환경·원장 보완의 네 합의**를 연결한 상세 설계다. 후속 이슈가 공유할 기준이며 제품 구현 완료를 뜻하지 않는다. 기준은 2026-10-03에 확인한 최신 통합 커밋 `e53ca21c18e1b4a333b7ae8f80148b46f59c069c`. 현재 코드와 설계의 차이를 읽기 대조했다. 제품 테스트·강제 종료 실험의 실행 결과를 담은 문서는 아니다.

## 이번에 추가한 일 — 원장이 잔고를 설명하도록

현재는 **체결 정산용 복식 원장**이 있다. 다만 초기 잔고·예약·취소 반환이 빠져 있어 전체 available/hold를 원장만으로 설명할 수 없다. 이 한계가 곧 현재 잔고 계산이 틀렸다는 증거는 아니다.

| 작은 PR | 추가할 결과 | 기존 복구/실행 이슈와 연결 |
| --- | --- | --- |
| [#71 초기 자금](https://github.com/0Chord/coin-exchange/issues/71) | 자금 출처 + 초기 available을 함께 기록 | #49가 시연 준비에 사용 |
| [#72 예약](https://github.com/0Chord/coin-exchange/issues/72) | available → hold 이동과 RESERVE 기록을 한 번 커밋 | #50이 접수 입력까지 연결 |
| [#73 취소 반환](https://github.com/0Chord/coin-exchange/issues/73) | 남은 hold → available과 RELEASE 기록을 한 번 커밋 | #57이 미완료 취소 복구에 사용 |
| [#74 대조](https://github.com/0Chord/coin-exchange/issues/74) | 원장 계산·DB 잔고·활성 예약을 비교 | #58이 재개/차단을 판단 |

수수료 없는 예시로 보면 **초기 1,000 → 예약 300 → 체결로 100 사용 → 남은 200 반환 = available 900, hold 0**이다. 원장 계산과 DB가 모두 이 값이어야 한다. 체결 정산 자체는 이미 있으며 여기서 중복 구현하지 않는다.

**추천 다음 작업은 #71이다.** 원장 보완을 한 PR에 묶지 않는다. #72는 별도로 진행할 수 있고, 이후 #50은 이미 준비된 예약·원장 원자성에 입력 기록만 연결한다. 지금은 설계·티켓 반영이며 제품 코드는 아직 바꾸지 않았다.

## 한 주문은 이렇게 이어진다

1. **예약과 입력 저장:** BUY 3개 요청을 검증하고, 주문 입력·접수 순서·예약·잔고 hold 이동·RESERVE 원장을 함께 저장한다. 여기까지 커밋되면 접수 확정이다. 큐에 들어간 것만으로는 확정하지 않는다.
2. **매칭 결과 저장:** 엔진이 1개 체결·2개 대기를 판단한다. 결과 이벤트 전체와 ‘이 요청의 결과 저장 완료’를 함께 커밋한다. 중간 이벤트 몇 개만 완료로 인정하지 않는다.
3. **자금 반영:** 저장된 체결마다 원장·양쪽 예약·잔고·수수료를 함께 반영한다. 한 요청에서 체결이 여러 개면 각 체결은 별도 트랜잭션이다. 모든 후속 처리가 끝나야 기존 정상 응답을 보낸다.
4. **재시작:** 새 요청을 막고 확정 결과로 주문장을 복원한다. 저장된 미정산 체결·미반환 취소를 먼저 끝낸 뒤, 결과가 없는 접수 요청을 이어 처리한다. 예약을 두 번 만들지 않는다.
5. **재개 판단:** 주문장·예약·정산 근거와 원장 계산·DB 잔고가 맞으면 마켓을 연다. 기록이 모순되면 이유를 남기고 닫아 둔다. 이 차단은 복구 성공이 아니다.

**세 종류의 별도 DB 경계다.** 정산은 체결마다 커밋하므로 총 횟수는 체결 수에 따라 늘어난다. 뒤쪽 실패가 앞선 커밋이나 메모리 매칭을 롤백하지 않는다. 3초 응답 대기 초과도 접수 취소·자금 반환·실행 중단을 뜻하지 않는다.

## 어느 순간 꺼졌는지에 따른 행동

| 종료 시점 | DB에 남은 사실 | 이어 할 작업과 중복 방지 | 재개 판단 |
| --- | --- | --- | --- |
| 큐 대기 / 예약 트랜잭션의 롤백 확인 | 접수 기록·새 예약 없음 | 미접수. 임의 주문 생성 없음. 클라이언트 재요청은 같은 주문 ID로 확인 | 정상 거절이면 다음 요청 가능 |
| 예약 커밋 후, 매칭 전 | 접수 입력 + 예약 + hold + RESERVE 원장 | 기존 예약으로 매칭. 같은 접수 키로 재예약 방지 | 결과 저장·자금 처리·대조 후 재개 |
| 메모리 매칭 후, 결과 저장 전 | 위 접수 근거만 남고 메모리 결과 유실 | 확정된 과거 결과로 엔진 복원 후 이 요청만 실행. 완료된 SUBMIT ID와 pending ID 구분 | 저장·자금 처리·대조 후 재개 |
| 결과 저장 후, 정산 전 | 완전한 결과 묶음, 정산 원장 없음 | 재매칭 없이 저장된 체결 정산. 체결별 sourceEventId로 완료 확인 | 모든 미완료 자금 처리·대조 후 재개 |
| 여러 체결 중 일부만 정산 | 앞 체결의 원장·잔고·예약 커밋 | 완료 키가 있는 체결은 재계산 전에 건너뛰고 나머지를 이벤트 순서대로 정산 | 나머지 처리·대조 후 재개 |
| 취소 결과 저장 후, 반환 전 | 성공 취소 이벤트, ACTIVE 예약 | 앞선 체결 정산 후 남은 예약만 반환. RELEASED와 RELEASE 원장으로 중복 방지. 취소 거절은 반환 없음 | 반환·대조 후 재개 |
| 정산/반환 커밋 후, 응답 전 | 정산 원장 또는 RELEASED 예약 + RELEASE 원장 | 기존 완료 근거를 확인하며 금전 재변경 없음. 응답 유실을 실패 주문으로 바꾸지 않음 | 다른 미완료 작업·불일치가 없으면 재개 |
| 복구 중 다시 종료 | 복구 중 커밋된 동일 완료 근거 | 빈 엔진을 다시 복원하고 미완료 효과만 처리 | 같은 대조를 마친 뒤 재개 |
| DB 커밋 결과 불명 / 기록 누락·모순 | 성공·실패를 확정할 근거 부족 | 커밋 결과 해결과 실제 기록 확인 전 재실행·반환 금지 | 원인을 남기고 차단. 복구 성공으로 집계하지 않음 |

DB 통신 오류로 커밋 성공 여부를 모르는 경우에는 **미접수라고 단정하지 않는다.** 해당 마켓을 멈추고 DB가 다시 읽힐 때 접수·결과·정산 근거를 확인한다. 정상 잔고 부족처럼 롤백이 확인된 거절과 구분한다.

재조회에서 행이 아직 안 보이는 것만으로 미접수라고 결론 내리지 않는다. 앞선 트랜잭션이 아직 완료 중일 수 있으므로, 그 결과가 해결된 뒤 동일 식별자로 재개 여부를 판단한다. 구체 연결·잠금 처리와 재시도 검증은 #50·51에서 다룬다.

## 상세 계약 — 필요한 부분만 펼치기

<details markdown="1">
<summary>1. 필요한 기록과 기존 데이터의 역할</summary>

‘복구 근거’는 하나의 거대한 상태 필드가 아니라, 같은 DB에 커밋된 입력·결과·금전 기록의 조합이다. 메모리와 현재 설정값은 과거 완료의 근거로 사용하지 않는다.

| 기록 | 담아야 할 최소 사실 | 원자 경계 / 담당 이슈 |
| --- | --- | --- |
| 새 접수 기록 | 내부 요청 ID, 마켓 처리 순서, 요청 종류, 주문/사용자 ID, 입력, 기록 버전. SUBMIT은 방향·가격·수량·LIMIT/GTC, CANCEL은 대상 주문·요청자. | SUBMIT은 예약·hold·RESERVE 원장과 함께 커밋(#72 기반의 #50). CANCEL은 엔진 호출 전에 저장(#51). |
| 기존 매칭 이벤트 + 결과 연결 | 요청 ID, 전체 이벤트 수와 순번 범위, 결과 저장 완료. 각 이벤트의 타입별 필수값. | 이벤트 묶음과 완료 표시를 하나로 커밋(#51). 기존 이벤트 일괄 저장을 재사용한다. |
| 기존 주문 예약 | 당시 요율·등급·정책 버전, 수수료 나머지, 원금/수수료 잔여 예약, ACTIVE/SETTLED/RELEASED | 예약·정산·반환의 기존 원자성을 유지한다. 현재 fee Bean으로 과거 주문을 다시 계산하지 않는다. |
| 개시·예약·취소 반환 원장 | 초기 자금 출처, 예약/반환의 원본 ID, 사용자·자산·금액 | 각각 잔고/예약과 한 커밋(#71~73). 체결 내부 반환은 기존 SETTLEMENT에 유지한다. |
| 기존 정산 원장 + 주문별 정산 상세 | 체결 식별자, maker/taker 주문, 각 실제 수수료와 자산, 확정된 0 수수료, 적용 정책 근거 | 한 체결의 잔고·예약 변경과 함께 커밋(#55). #62는 이 사실을 조회한다. 과거 수수료를 현재 잔량으로 역산하지 않는다. |
| 복구 형식·마켓 정의 | 기록 버전, base/quote 자산, 수량 scale, 해석/계산 규칙 버전의 호환성 | #50/#51에서 기록하고 #58/#59에서 검사. 값이 달라 해석 불가능하면 차단한다. 스키마·클래스 이름은 각 이슈에서 정한다. |

새 접수 기록은 요청 의도만 보존한다. 잔고 전체 복사본, 주문장 스냅샷, 별도 이벤트 플랫폼·분산 로그는 이번 설계에 추가하지 않는다. 오래된 데이터의 보관·압축·스냅샷은 시작 시간이 실제 문제가 될 때 후속으로 판단한다.

**확인한 현재 한계:** reserve/release와 초기 잔고 준비의 원장 기록이 빠져 있다. **추가 합의:** #71~73에서 빈틈을 메우고 #74에서 개시 기록부터 쌓은 원장으로 사용자 available/hold를 재계산해 실제 DB 값과 대조한다. 유지된 DB 잔고·예약에 미완료 효과를 이어 적용하며, 대조 실패를 자동 덮어쓰기로 고치지는 않는다.

- 개시 자금은 개발 환경에서 명시적으로 준비하는 시연 자금이다. DB 전체가 새것일 필요는 없다. 기존 거래·잔고를 초기값으로 덮어쓰지 않고, 대상 계정의 개시 여부와 동일 준비 ID를 확인한다. 사용자 AVAILABLE의 대변과 자금 출처 상대 계정의 차변을 기록한다. 초기 hold는 0이며 실제 입금 증거로 표현하지 않는다. 0 잔고 행 준비에 빈/0 분개는 만들지 않는다.
- 예약은 AVAILABLE 차변·HOLD 대변, 취소 반환은 HOLD 차변·AVAILABLE 대변이다. 사용자 총액은 그대로지만 사용 가능/예약 계정 간 이동을 남긴다. 금액·예약·원장은 함께 커밋/롤백한다.
- 체결의 가격 개선·미사용 예약 반환은 기존 SETTLEMENT에 포함된다. `BalanceStore.release()`마다 새 분개를 붙이면 중복되므로 업무 서비스에서 완성된 원장을 기록한다.
- 현재 사용자 AVAILABLE/HOLD는 대변−차변으로 계산한다. 출처 등 다른 성격의 계정까지 같은 방향으로 일반화하지 않는다. 여러 조회는 같은 DB 스냅샷에서 수행한다.
- 원장·잔고·예약에 나타난 대상의 합집합을 대조해 한쪽 누락, hold 부족/초과, 고아 예약을 놓치지 않는다. DB 읽기 실패는 통과나 금액 불일치가 아닌 검증 불가다.
- 활성 예약 합과 DB hold 대조는 이번 단일 마켓·관련 자산에서 다른 목적 hold가 없다는 전제다. 타 목적 hold가 생기면 소유 근거를 별도로 설계한다. 과거 데이터 이행·잔고 자동 재생성·외부 증거 없는 전체 기록 삭제 탐지는 이번 보장이 아니다.

<details markdown="1">
<summary>2. 처리 순서·중복 방지·취소 요청의 식별</summary>

- 기존처럼 한 마켓 worker 안에서 접수 저장 → 매칭 → 결과 저장 → 정산/반환을 끝낸 뒤 다음 요청을 실행한다. 큐 밖에서 예약을 먼저 커밋하는 병렬 경로는 만들지 않는다.
- 마켓 처리 순서는 저장 시각이 아닌 명시적인 증가 순번으로 남긴다. 롤백으로 번호가 비는 것과 결과 이벤트가 누락된 것을 구분한다. `MAX(sequence)` 하나만으로 기록 완전성을 판정하지 않는다.
- 정상 거절은 다음 요청을 막지 않는다. 접수 이후 실패와 커밋 결과 불명의 저장 오류는 후속 요청을 막는다. 따라서 정상 기록에는 결과 없는 접수 요청이 있다면 마켓의 마지막 요청 하나뿐이어야 한다. 그 뒤 완료 요청이 있으면 전제 위반으로 차단한다.
- 이 마지막 미완료 요청 규칙은 결과 저장 후 정산·반환이 덜 끝난 경우에도 적용한다. 앞 요청의 후속 자금 효과가 미완료인데 다음 접수 기록이 있으면 정상 중단 상태로 처리하지 않고 불일치로 차단한다. 실제로 처리가 덜 된 것과 완료 표식 캐시만 늦은 것은 원장·예약 근거로 구분한다.
- SUBMIT의 업무상 중복 키는 `(marketId, orderId)`다. 이미 접수된 동일 입력은 재예약·재매칭하지 않는다. 같은 키의 다른 소유자/방향/가격/수량은 충돌이며 원래 주문을 덮어쓰지 않는다. 구체 HTTP 응답은 #65에서 정한다.
- 엔진의 `seenOrderIds`에는 **매칭 결과가 확정된 SUBMIT만** 복원한다. 접수만 된 pending 주문 ID는 DB 접수 기록으로 새 중복 요청을 막되, 엔진의 첫 실행을 막지 않는다.
- CANCEL은 같은 주문을 여러 번 요청할 수 있으므로 서버 내부 요청 ID로 각각 기록한다. 주문 ID와 요청 ID를 혼동하지 않는다. 재시작은 저장된 취소 요청 ID를 이어 실행한다. 사용자가 HTTP DELETE를 다시 보냈을 때 과거 응답까지 그대로 재생하는 외부 취소 요청 키는 이번에 추가하지 않는다. 반복 취소도 금전은 한 번만 반환한다.
- 정산 완료 키는 기존 `MATCHING:{marketId}:{engineSequence}`를 재사용한다. 원장 존재를 **남은 예약으로 재계산하기 전** 확인한다. 같은 키의 다른 체결 내용이나 잘못된 거래 종류는 정상 중복으로 무시하지 않는다. 조회·원자 반영·유일성 제약의 결합은 #55가 검증한다.
- 반환은 저장된 `OrderCancelled`에만 연결한다. RELEASED와 RELEASE 원장의 대상·금액이 맞으면 완료, ACTIVE면 잔여금 반환과 RELEASE 기록을 함께 커밋한다. 한쪽 근거만 있으면 정상 재시도로 무시하지 않는다. SETTLED 또는 누락 예약은 취소 기록과 모순인지 검사하고 임의 반환하지 않는다.
- 금전 완료는 원장·예약으로 판정한다. 별도 ‘전체 완료’ 캐시를 두더라도 원래 근거에서 재생성할 수 있어야 하며, 캐시 저장 실패 때문에 금전을 재반영하지 않는다.

현재 `beforeMatching`에서 어떤 예외가 나도 실행기는 그 요청만 실패시키고 다음 요청을 허용한다. 따라서 **커밋 결과 불명인 인프라 오류를 마켓 차단으로 분류하는 보강은 #50/#51의 필수 범위**다. 기존 정상 거절 흐름 전체를 차단하도록 넓히지는 않는다.

</details>

<details markdown="1">
<summary>3. 주문장 복원과 자금 처리를 분리하기</summary>

확정 결과는 저장된 순번대로 순수 코어에 적용한다. 이 경로는 DB·publisher·정산 callback을 호출하지 않는다. `MatchingEngine.process()`로 완료 주문을 다시 매칭하는 경로와 구분한다.

| 저장된 결과 | 주문장에 적용할 일 |
| --- | --- |
| TradeExecuted | 존재하는 maker의 잔량을 줄이고 0이면 제거한다. taker는 이 요청의 입력·누적 체결로 검증하되 아직 주문장에 없을 수 있다. |
| OrderEnteredBook | 이 요청의 미체결 잔량을 해당 가격의 뒤에 넣는다. 앞 Trade로 계산한 taker 잔량과 맞는지 확인한다. |
| OrderCancelled | 소유자·취소 잔량을 대조하고 주문을 제거한다. 자금 반환은 여기서 실행하지 않는다. |
| OrderCancelRejected | 주문장을 바꾸지 않고 순번만 이어간다. 거절 대상 주문 ID를 새 SUBMIT 처리 이력으로 추가하지 않는다. |

이번 복구 v1 계약에서 SUBMIT 결과는 TradeExecuted 0개 이상 뒤 OrderEnteredBook 최대 1개이며, 체결 합계 + 진입 잔량 = 입력 수량이어야 한다. 유효한 양수 수량의 LIMIT/GTC는 결과가 적어도 1개다. CANCEL 결과는 성공 또는 거절 이벤트 정확히 1개다. **0개 결과 + 저장 완료 표시는 정상 성공이 아니다.** 원래 주문 수량은 OrderEnteredBook에 없으므로 접수 입력·예약 initialQuantity와 대조해 내부 주문을 복원한다.

전량 체결된 taker는 OrderEnteredBook이 없어도 완료된 SUBMIT 접수 기록으로 처리한 ID를 복원한다. 다음 이벤트 번호는 검증한 전체 결과의 마지막 번호 + 1, 완전히 빈 새 마켓은 1이다. 이번 복구 v1은 현재 엔진의 1부터 연속하는 이벤트 번호를 유지하며 결과 범위·개수·실제 행·앞뒤 연결을 함께 대조한다. 현재 저장 payload에 이미 기록 버전이 있다는 뜻은 아니다. 접수 순번의 롤백 공백을 이벤트 누락과 동일하게 다루지 않는다.

복구 순서는 **새 요청 차단 → 형식/결과 묶음 검증 → 확정 결과로 빈 엔진 복원 → 저장 이벤트 순서대로 미완료 자금 처리 → 마지막 pending 요청 실행 → 최종 대조 → 접수 재개**다. 재시작 전부터 예약만 있던 pending SUBMIT은 당시 입력과 정책을 사용하고 기존 hold를 재사용한다.

도메인 `matching`에는 순수 복원·불변식만 둔다. 기록 읽기와 복구 순서 조율은 `app-api` application, SQL/JPA는 infrastructure/persistence, 시작/설정 연결은 config `@Bean`에 둔다. 구체 타입명·허용 package 추가는 각 작은 이슈에서 기존 컨벤션과 맞춘다. 도메인에 DB 호출을 넣거나 internal 주문장 객체를 외부로 노출하지 않는다.

</details>

<details markdown="1">
<summary>4. 조회 결과와 재개/차단 기준</summary>

주문 상태·금전 상태·마켓 상태를 한 단어로 뭉치지 않는다. 아래는 의미 계약이며 외부 JSON 이름·코드는 각 API 이슈에서 정한다.

- **주문:** 접수·매칭 대기 / 미체결 대기 / 부분 체결 / 전량 체결 / 잔여 취소. 미접수 거절은 새 주문을 만들지 않는다. 취소 거절은 기존 주문 상태를 바꾸지 않는다.
- **수량:** 매칭 결과 확정 후에는 최초 수량 = 체결 수량 + 주문장 대기 수량 + 취소 수량이다. 접수만 된 요청은 입력 3개·매칭 대기로 표현하며 3개가 이미 주문장에 있다고 표시하지 않는다. 예: 3개 중 1개 체결 후 취소면 체결 1·대기 0·취소 2다.
- **금전 처리:** 결과 미확정 / 후속 정산·반환 미완료 / 필요한 후속 처리 완료. 체결은 확정됐지만 정산은 미완료일 수 있다. 체결이 없는 정상 대기는 후속 효과가 없어 완료로 표현할 수 있다.
- **마켓:** 복구 중 / 재개 가능 / 불일치로 차단 / 종료 중. 복구 중에도 DB로 확정된 결과를 보여줄 수 있으나 미완료·대조 전 상태를 함께 알린다. 데이터가 모순되면 정상 잔량·잔고를 임의 계산해 확정값으로 내지 않는다. DB를 못 읽는 것과 주문이 없는 것도 구분한다.

재개를 막는 최소 사례는 입력 없는 예약, 결과 marker와 실제 이벤트의 개수·범위 불일치, 모르는 기록 버전, maker/소유자/잔량 모순, 완료 원장과 효과의 모순, 성공 취소와 예약 상태의 모순, 복구 뒤 남은 미정산, 원장과 available/hold의 차이, 활성 예약과 hold 불일치다. DB 읽기 실패로 대조를 못 해도 재개하지 않는다. 원래 코드의 오류를 추정 수정하거나 데이터를 자동 삭제하지 않는다.

**현재 합의: 아직 배포 전이므로, 현재 기록 구조에 맞는 개발·테스트 데이터를 준비하고 같은 DB를 유지한 채 재시작 복구를 검증한다.** 새 DB를 별도로 만드는 것은 필수 조건이 아니다. 구형 DB인지 판별하는 기능, 과거 형식별 호환 차단, 기존 데이터 자동 전환은 이번 구현 범위에 넣지 않는다.

**계속 검사할 것은 실제 기록이다.** 주문 입력·결과·예약·원장이 빠졌거나 모순되고, 잔고 대조가 맞지 않거나 기록을 읽을 수 없으면 원인을 남기고 주문 처리를 시작하지 않는다. DB가 예전에 만들어졌다는 이유만으로 차단하지 않는다.

개발 데이터를 어떻게 준비할지는 구현·테스트 환경에서 정한다. 준비가 끝난 뒤에는 서버 종료 전후의 DB와 거래 기록을 그대로 유지해야 복구를 검증할 수 있다. 이번 명세 수정으로 기존 데이터를 삭제·초기화하지 않는다.

</details>

<details markdown="1">
<summary>5. 독립된 수용 예시와 후속 검증</summary>

설명용 마켓은 수량 scale 0, 가격 100, 수수료 0으로 둔다. A의 최초 quote 잔고는 300, B는 200, C의 최초 base 잔고는 1이고 나머지 해당 잔고와 초기 hold는 0이다. 실제 마켓 설정을 0 수수료로 바꾸자는 결정이 아니다.

| 사례 | 기대 결과와 근거 | 구현·검증 이슈 |
| --- | --- | --- |
| 새 계정 1,000 준비 → 300 예약 → 100 정산 → 200 취소 반환 | available/hold가 1,000/0 → 700/300 → 700/200 → 900/0. 각 단계 원장 계산과 DB 일치. 같은 사건 재시도 시 추가 분개·금전 변화 없음. | #71~74 |
| 원장 누락 / DB available 1 증가 / hold 총액만 일치 / DB 조회 오류 | 각각 차이·원인을 보고하며 자동 보정 없음. DB 오류는 검증 불가. #58에서 재개 차단. | #74·58·70 |
| BUY A 3개, BUY B 2개를 같은 가격으로 접수하고 SELL C 1개 체결 | 이벤트 1=A 대기3, 2=B 대기2, 3=A/C 체결1. 복원하면 A2→B2, C는 주문장 없음. 처리한 제출 ID=A/B/C, 다음 이벤트4. 시간값 대신 저장 순서로 FIFO 확인. | #52·53 |
| 위 체결3은 저장됐지만 미정산 | 주문장 A2와 예약 A3의 일시 차이를 곧장 손상으로 단정하지 않는다. 체결3 정산 후 A hold200·base1, B hold200, C base hold0·quote100. 그 후 대조한다. | #55·56·58 |
| A 잔여2 취소 후 반환 전에 종료 | 취소 이벤트4로 A를 제거. B2는 유지. A의 hold200만 available로 반환. 다시 복구해도 반환 추가 없음. 다음 이벤트5. | #57·69 |
| 두 체결 중 첫 체결만 정산 완료 | 첫 원장·예약·잔고·수수료·나머지 불변. 둘째만 추가 반영. 같은 복구를 두 번 해도 동일. | #55·56·68 |
| 수수료 나머지를 남긴 부분 체결 후 재시작 | 예약에 저장한 당시 maker/taker 요율과 나머지를 이어 사용. 현재 Bean 요율이 달라도 과거 주문 수수료를 바꾸지 않음. 정산 확정 0과 미정산을 구분. | #55·62·68 |
| 예약 커밋 후 종료 / 메모리 매칭 후 저장 전 종료 | 모두 접수 기록에서 한 번 실행. 재예약 없음. 기존 확정 이벤트·자금 효과는 반복하지 않음. | #50·51·54·67 |
| 결과 저장 성공 응답만 유실 | DB에 완전한 결과가 있으면 그 결과 복원. 매칭을 다시 실행하지 않음. DB 판단이 불가능하면 마켓 차단 유지. | #51·58·67 |
| 접수 전 잔고 부족 | 새 접수/예약/hold 모두 없음. 엔진 호출 없음. 같은 마켓 다음 정상 주문은 처리 가능. | #45·50 |
| 취소 거절 저장 / 완전히 체결된 주문 ID 재접수 | 거절은 순번만 복원·금전 변화 없음. 완료 SUBMIT의 ID는 재사용 불가. | #53·57·65 |
| 이벤트 한 개 삭제, 0개 결과 완료, 앞 요청 미정산인데 뒤 접수 존재, 읽을 수 없는 기록 버전 | 빈 주문장으로 정상 시작하지 않음. 누락/해석/순서 문제를 알리고 차단. 정상 복구 성공으로 집계하지 않음. | #51·58·59·70 |

기존 테스트는 예약·정산·반환의 트랜잭션, 잔량·FIFO·번호, 수수료 나머지, 실패 후 후속 요청 차단을 검증한다. **durable 접수 기록과 실제 프로세스 재시작은 새 검증 대상**이다. 이번 설계에서 기존 테스트를 재실행하지 않았다.

후속 구현은 순수 복원 테스트 → 실제 PostgreSQL 커밋/롤백·중복 테스트 → 실제 서버 강제 종료·같은 DB 재시작 순서로 근거를 더한다. 단위 테스트에서 예외를 던진 것만으로 OS 프로세스 강제 종료를 검증했다고 하지 않는다.

#43의 설계 산출물에는 새 복구 기능과 그 실행 테스트를 포함하지 않는다. 기존 테스트 파일은 아래 코드 근거와 연결하고, 실행할 명령·작업 폴더·실제 결과는 각 후속 구현에서 기록한다. DB 경계는 Testcontainers/PostgreSQL에서, 서버 종료 경계는 같은 DB를 유지하는 별도 프로세스에서 검증해야 한다.

문서 PR에서 발견한 TestKit 임시 폴더 정리 오류는 별도로 수정하고 회귀 테스트를 추가했다. 구조 검사를 실행하는 환경의 보완이며, 이 테스트나 기존 CI의 통과가 새 접수·복구 기능을 검증한 것은 아니다. 해당 실행 결과는 PR에서 확인한다.
