## 메모리가 무한히 증가하는 시험기로 만들지 않기

기존 측정기는 주문별 다섯 개 Long 배열에 모든 전송·응답·완료 시각을 저장한다. 초당 3만 건으로 600초면 기본 배열만 720MB이며 통계 배열도 필요하다. 이는 실제 엔진 OOM이 발생했다는 뜻이 아니다.

이번에는 같은 연결·클러스터·자금 상태에서 최대 10초/100만 표본씩 기존 phase를 반복한다. 구간의 결과와 ACK를 모두 확인한 뒤 전체 히스토그램·합계만 남기고 배열 참조를 해제한다. 누적 BUY 순번과 ACK floor는 계속 증가한다. 배열 생성·집계·구간 drain 공백도 전체 TPS 분모에 포함한다. 측정 중 금융 상태를 초기화하지 않았다.

메모리 관측 세 차례의 컨테이너 사용량은 클라이언트 508.4→509.4→509.6MiB, 리더 node0 548.3→585.8→608.5MiB, 나머지 노드는 약437~480MiB였다. 컨테이너 기준의 드문 표본이며 JVM Heap만을 측정한 값이나 모든 누수 부재의 증명은 아니다. 이번 실행은 OOM으로 종료된 노드 없이 정상 완료했다.

엔진도 과거 주문 객체를 무제한으로 유지하는 구조가 아니다. 확인된 결과 정리, 요청 창과 미체결·대기 주문 한도를 사용한다. 다만 이번 시험은 많은 계정·미체결 주문의 메모리 용량 시험이나 장애 주입 시험은 아니다.

## 정합성·정리

세 노드의 최종 상태 지문은 `20ecc7e9dbb3fb8d5025648147e208b79b976b8b0c99d47506003be858aa25eb`로 같았다. 정확한 BUYER/SELLER ACK floor, 잔고·예약·수수료·세 마켓 잔량, 마지막 접수 순번, pending=0·retainedReceipts=0을 기존 제어기로 검증했다. 완료 표식 손상·누락 및 표본 한도 소진 없이 종료했다. 측정 구간의 각 노드 접수·실행 callback 수도 측정 주문 수와 일치했다.

세 노드 `/records` 실제 할당량은 최대 **16.453GiB**였다. 상한24GiB·조기중단23GiB·host 여유8GiB를 유지했으며, 최소 host 여유는 **60.99GiB**였다. 종료 후 이번 실행의 컨테이너와 named volume이 제거됐다. Docker VM의 반환 지연 때문에 host 파일 여유가 같은 순간 같은 양만큼 늘어난다고 단정하지 않는다.

독립 대조에서 원본 이벤트·전체 실행 파일 SHA·세 노드 최종 잔고/수수료 산식·정리 로그가 일치했다. 원자료 guard 설명에 짧은 시험의 256MiB 문구가 남아 있으나, 실제 숫자 설정과 조기중단 검사는24−23=1GiB 여유였다.

측정기 관련 Kotlin 24개·제어기 순수 검사14개가 통과했다. 작성 대화를 상속하지 않은 검토에서 발견한 인코딩 후 구간 기한 재검사 문제를 수정하고 재확인했다. 제품의 기존 회귀 검증을 이번 지속 부하가 대체하지 않는다.

## 기업 공개 사례와의 구분

Coinbase International Exchange 담당자의 발표는 활성 상태를 메모리에, 입력을 append-only 로그에 두고 스냅샷·후속 로그로 복구하는 구조를 설명한다. [담당자 발표·질의응답](https://www.infoq.com/presentations/exchange-systems-cloud/)

정리 후 생성한 이미지 태그2개와 중복 실행 배포본도 제거했다. 원본 검증 배포본·테스트 클래스 overlay·전체 지문·원자료는 보존했다. 마지막 host 여유 공간은 약 **77.10GiB**였다.
