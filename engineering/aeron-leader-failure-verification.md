# 리더 종료 뒤 생존 노드가 경고 때문에 함께 종료되지 않게 하기

## 확인한 문제

통합 커밋 `a69d9c21a9f16ab8a6681326afc17f6015cbd971`의 실제 개발 노드 세 개를 같은 호스트의 독립 Docker 컨테이너와 JVM에서 실행했다. U1에게 1,000 USDT를 준비하고 R1/O1 주문에 300 USDT를 예약해 세 사본의 사용 가능 700·예약 300, 최초 승인, 순번 1과 원장을 대조했다.

리더 컨테이너에 SIGKILL을 보낸 뒤 나머지 두 프로세스도 종료됐다. 생존 노드의 종료 원인은 `ClusterEvent: WARN - leader heartbeat timeout`이었다. 기존 공통 오류 핸들러가 WARN도 `fail()`에 전달해 노드를 닫았기 때문이다. 정상 세 노드 복제 검사는 이 장애 경계를 실행하지 않았다.

Aeron 1.53.3의 `ConsensusModuleAgent.enterElection()`은 리더 heartbeat가 끊기면 WARN을 기록한 뒤 재선출을 시작한다. 애플리케이션이 그 경고에서 먼저 종료되면 라이브러리의 복구 절차를 이어갈 수 없다. MediaDriver만 WARN을 기록하고 계속하도록 구성돼 있던 차이도 확인했다.

## 이번 변경의 계약

- Aeron 런타임의 WARN은 각 컴포넌트의 실제 오류 로그·카운터에 남기고, 라이브러리가 다음 처리를 이어가게 한다.
- ERROR·FATAL·일반 예외는 기존처럼 해당 개발 노드를 중단한다. 메시지 문자열이 WARN으로 시작한다는 이유로 일반 예외를 허용하지 않는다.
- 코어 계산·반영 실패는 어댑터의 기존 `onFatal` 경로로 계속 중단한다. 잘못된 자금 상태를 정상 상태로 돌리는 기능은 추가하지 않는다.
- 오류 분류를 Driver·Archive·Consensus·Service에 같은 핸들러로 적용한다. Snapshot, 기존 기록 재시작, 죽은 노드 재합류 계약은 변경하지 않는다.

## 테스트를 읽는 방법

`DevelopmentFundingNodeTest`의 새 Consensus 경고 사례는 실제 노드와 UDP 클라이언트로 먼저 자금을 준비한다. 그 노드에 설치된 실제 counted error handler에 Aeron의 heartbeat 경고를 전달한다. 경고가 실제 오류 로그에 남고, 노드가 열려 있으며, 다른 사용자의 새 자금 준비가 완료되는지 확인한다.

반례는 ERROR·FATAL·일반 예외다. 일반 예외에는 WARN이라는 문자열을 넣어 문자열 비교로 예외를 무시하지 않는지도 확인한다. 이 사례는 노드가 닫히고 최초 오류가 유지되는지 검사한다. 오류 주입 테스트 자체가 실제 Raft 재선출을 증명하지는 않는다.

## 실제 리더 종료 검사의 수용 기준

1. 새 세 노드 실행과 실제 준비 상태, 동일 설정, 각 프로세스·기록 격리를 확인한다.
2. R1 승인 응답과 세 사본의 같은 적용 위치에서 잔고·예약·최초 결과·원장 원본을 독립적인 기대값과 대조한다.
3. 실제 LEADER 컨테이너를 SIGKILL하고, 종료 코드 137·OOM 아님·대상 식별자를 기록한다.
4. 원래 생존한 두 노드에서 더 높은 리더 임기로 바뀌고, 새 클라이언트가 동일 R1의 순번 1과 최초 승인을 받는지 확인한다. 잔고 700·예약 300과 원장 건수는 그대로여야 한다.
5. R2/O2에 100 USDT를 추가 예약해 순번 2·사용 가능 600·예약 400으로 진행하는지 확인한다. 새 접수도 처리되는지 확인하는 단계다.
6. 생존 노드의 컨테이너·프로세스 시작 식별자가 바뀌지 않았고, 마지막 상태 이후 오류·비정상 종료가 없는지도 대조한다. 의도적으로 죽인 노드를 정상 종료 대상으로 세지 않는다.

세 노드 상태 확인 후 리더를 종료하는 사례다. 응답과 강제 종료 사이의 모든 실패 위치, 기존 클라이언트 연결 복구, 전체 재시작·노드 재합류·다중 호스트·AZ·디스크 유실·Snapshot 복원을 검증한 것으로 확대하지 않는다. 다른 리더 임기의 Archive 원문 재생 검사는 기존 도구가 지원하지 않아 별도 과제다.

## 실행 근거

수정 코드 고정점은 `d7b8713d60ccfd8a2b77058134da8144954b65db`이며 통합 기준은 `a69d9c21a9f16ab8a6681326afc17f6015cbd971`이다. 2026-10-23 KST에 같은 Apple M1 Pro 호스트의 독립 Docker 컨테이너·JVM 세 개에서 실행했다. 노드마다 1.5 CPU·512 MiB JVM heap을 주고 Archive·Catalog·Consensus의 sync level 2를 유지했다.

실제 성공 실행 ID는 `evidence-ha-20261022-160443-4e6f00`, `evidence-ha-20261022-160510-0df70c`, `evidence-ha-20261022-160531-eca2ad`다. UTC 기반 실행 ID이므로 KST 실행 날짜와 다르다. 입력·checkpoint·종료 기록과 세 Archive 볼륨 ZIP을 로컬 검증 자료에 보존했다. 독립 원본 감사에서도 세 실행의 의미 불일치는 없었다.

실험에서는 Docker가 종료된 컨테이너의 DNS 항목을 없애는 영향을 피하도록 새 클라이언트에 기동 시 캡처한 노드 주소를 제공했다. 각 클라이언트는 별도 고유 응답 주소를 썼으며, 생존한 두 서비스가 더 높은 같은 임기를 관찰한 뒤 새 연결을 시작했다. 리더 주소를 직접 지정하거나 죽은 노드를 자동 재기동하지 않았다. 첫 성공 이후에도 새 실행으로 반복했다.

수정 전에는 heartbeat WARN 때문에 생존 노드가 종료됐다. 수정 후 초기 실험에서 새 클라이언트 연결이 시간 초과되거나 종료된 멤버 이름을 해석하지 못한 실행도 별도로 보존했다. 이 실패들을 성공 횟수에 합산하거나 기존 연결의 자동 복구가 입증됐다고 해석하지 않는다. 관측한 약 11초대 새 임기 확인에는 기본 heartbeat 대기와 폴링이 포함되므로 순수 선출 시간·RTO로 제시하지 않는다.

이번 결과는 로컬 후보 코드의 단일 리더 프로세스 종료 사례다. 통합 브랜치의 원본이 그대로 이 검사를 통과한 것도, 모든 성공 응답 유실 0·운영 고가용성·무중단이 입증된 것도 아니다.

참고: [Aeron Cluster 오류의 심각도](https://aeron.io/docs/aeron-cluster/cluster-errors/), Aeron 1.53.3의 `ConsensusModuleAgent.java`, `ClusterEvent.java`, `ConsensusModule.Context`.
