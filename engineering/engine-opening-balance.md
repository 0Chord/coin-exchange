# #95 · 주문에 쓸 테스트 자금을 한 번 지급하기

**주문 테스트에 쓸 초기 잔고를 준비했다. 같은 지급 요청을 다시 보내도 돈이 늘어나지 않는다.** 실제 입금 기능이나 서버 시작 시 자동 지급은 만들지 않았다. 호출자가 준비 요청을 실행해야 한다.

예: **1,000 USDT 지급 → 주문에 300 USDT 예약 → 같은 지급 요청 재전송 → 사용 가능 700 USDT·예약 300 USDT 유지.** 응답은 ‘처음 1,000 USDT를 지급한 결과’이며, 현재 잔고를 뜻하지 않는다.

**검증 상태:** 로컬 구현·필수 검사·독립 리뷰 완료. PR·CI·병합의 최신 상태는 GitHub에서 별도로 확인한다. [합의한 명세](engine-opening-balance-spec.md) · [다음 작업 순서](aeron-admission-plan.md).

| 이번 흐름 | 결과 |
| --- | --- |
| 처음 보내는 지급 요청 | 현재 계정이 미사용인지 확인하고 잔고·지급 원본·OPENING 원장을 함께 기억한다. 주문 순번은 늘리지 않는다. |
| 같은 준비 ID·같은 사용자·자산·금액 | 첫 원장 ID·시각을 다시 반환한다. 지금의 잔고를 바꾸지 않는다. |
| 같은 ID인데 내용 변경 | 요청 내용 충돌. 첫 기록을 덮어쓰지 않는다. |
| 새 ID로 이미 사용한 계정에 지급 | 추가 지급 거절. 다른 사용자나 다른 자산은 별도로 준비할 수 있다. |
| 검증 중 잘못된 값·ID 충돌 | 상태를 쓰기 전에 중단한다. 수정한 요청을 다시 보낼 수 있다. |
| 반영 구간에서 예외 또는 Error | 원래 오류를 전달하고 그 상태 객체를 차단한다. 일부 반영을 되돌렸다고 보장하지 않는다. |

준비 결과와 현재 잔고를 구분하는 이유: 지급 당시의 `OpeningBalanceResult`는 ‘얼마를 언제 어떤 원장 ID로 지급했는가’다. 주문에 돈을 묶어도 이 과거 사실은 바뀌지 않는다. 현재 쓸 수 있는 돈은 `snapshot().balances`에서 따로 관찰한다. 이 둘을 섞으면 재전송할 때 돈을 다시 채우는 오류가 생길 수 있다.

OPENING 두 분개는 기존 규칙 그대로다. 1,000 USDT 사례는 시스템의 개발 자금 계정 차변 1,000 / 사용자의 사용 가능 계정 대변 1,000이다. 사용자 예약 계정은 이때 바꾸지 않는다. 이후 주문 예약은 별도의 RESERVE 기록이다.

[실제 반영 구간](../domain-trading/src/main/kotlin/com/exchange/core/trading/OrderAdmissionState.kt#L144)은 잔고·준비 기록·원장 ID 사용 이력 쓰기 앞에서 차단 표시를 켠다. 쓰기를 모두 마친 경우에만 끈다. 중간 오류를 잡아 성공으로 바꾸거나 `finally`에서 무조건 해제하지 않는다. 차단 뒤에는 신규·반복 지급, 두 주문 입구와 정상 조회를 거절하며 `isBlocked` 진단만 가능하다.

`현재 잔고가 0이어도`의 잔고 변경, `개시 사건 ID 충돌`의 이력 주입과 쓰기 오류 주입은 테스트용 리플렉션이다. 실제 입출금·정산·장애 복구 기능이 추가된 것이 아니다. 쓰기 장애 래퍼는 실제 도메인 상태의 collection에서 실패만 통제하며, 가짜 거래 계산기는 쓰지 않는다.

관찰 객체 전체 비교는 **같은 상태의 무변경 검사**에 사용한다. 독립 상태 둘을 비교할 때는 참조·해시 대신 후보·원장·요청의 실제 필드로 풀어 비교한다. 이 유한 입력열의 재현 확인은 모든 입력·JVM·실제 복제 노드를 검증한 결과가 아니다.

<summary>실행 기록과 독립 리뷰</summary>

- 최초 세 테스트는 동작 없는 입구에서 `UnsupportedOperationException`으로 실패했다. API 컴파일 오류나 환경 실패를 TDD Red로 세지 않았다. 기존 지급 규칙을 연결한 뒤 세 테스트는 통과했다.
- 후속 오류 주입 테스트에서 한 번 실패했다. 새 지급에도 기존 원장 ID를 재사용해 쓰기 지점 전에 충돌한 **테스트 준비 오류**였다. 새 원장 ID로 준비를 바로잡았으며 제품의 충돌 검사를 약화하지 않았다.
- 테스트 의도 검토에서 신규 지급 차단 사례가 이미 사용한 계정의 충돌로도 통과할 수 있음을 발견했다. 미사용 사용자·미사용 원장 ID로 바꾸고 정확한 차단 오류까지 대조했다. 기대 정책이나 제품의 충돌 검사를 낮추지 않았다.
- 신규 테스트 17개 정의, 내부 반복 입력은 위 표에 별도로 표시했다. 실제 실행: domain-ledger 39개·domain-trading 99개(신규 17개 포함)·architecture-tests 375개 모두 실패·오류·skip 0. 필수 운영 검사 P01~P09 보고서와 전체 ktlintCheck도 통과했다. 테스트 보강 뒤 domain-trading:test·해당 모듈 ktlintCheck를 다시 통과했다. 작성 대화를 상속하지 않은 별도 리뷰어가 격리 snapshot `review-snapshot-1`에서 같은 필수 검사를 직접 실행하고 전체 변경을 검토했다. 범위 안에서 확인된 미해결 결함은 없다. 이는 모든 미래 버그가 없다는 뜻은 아니다.

<summary>문답과 다음 작업</summary>

사용자 질문: “왜 개발용 자금을 명시적으로 준비하는 이유가 뭐야?”

설명: 실제 입금 기능이 없는 개발 단계에서 주문에 사용할 돈을 준비한다. 서버 시작 때마다 자동 지급하지 않고 직접 요청할 때 한 번만 지급한다. 같은 요청을 다시 보내도 돈을 늘리거나 주문에 묶인 돈을 초기화하지 않는다. 기존 ‘빈 메모리 엔진’ 설명보다 이 목적을 먼저 읽도록 바꿨다.

학습 Ask: “최초 지급 결과와 현재 잔고가 다른 이유 / 재전송과 추가 지급 요청의 차이 / 반영 도중 차단 이유 중 무엇을 더 자세히 보고 싶은가?” 사용자는 “최초 지급 결과와 현재 잔고가 다른 이유 (추천)”를 선택했다. 첫 지급 결과는 과거 지급 기록이며 현재 잔고와 다르다는 설명을 위 코드 읽기와 대표 사례에 보강했다. 별도 선택 이유나 이해 완료 답변은 없으므로 추측하지 않는다. 기존 재전송 계약의 합의는 [명세 문답](engine-opening-balance-spec.md)에 보존했다.

다음 #96은 이 지급 요청·응답의 Protobuf 변환이다. #97부터 실제 Aeron 통신을 연결한다. 이번 구현으로 그 기능까지 완료했다고 표시하지 않는다.
