## 결정

남아 있던 세 후보를 각각 비교하고 조합까지 검증했다. **불변 매칭 결과 재사용만 유지하고, 조건부 worker 깨우기와 테스트 클라이언트의 단일 디코딩은 제외했다.** 제외한 다섯 파일은 시험 전 기준 소스와 바이트 단위로 같게 복원했다. 모든 후보의 원문과 불리한 결과도 보존했다.

| 후보 | 실제 변경 | 최종 결정 | 근거 |
|---|---|---|---|
| A · 불변 매칭 결과 재사용 | 이미 소유권이 고정된 `SubmitOrderPlan.events`를 전체 결과 검증에 전달해 임시 결과 객체·목록 복사를 줄임 | 유지 | 완전성 검증을 그대로 유지하면서 세 노드의 네 비교 쌍 모두 할당량이 약 32–62 B/order 감소. 엔진 반복 진단 중앙값도 개선. 세 노드 TPS 향상은 확정하지 않음 |
| B · 조건부 worker 깨우기 | 소비자가 대기할 때만 메트릭 worker를 깨움 | 제외 | A+C에 B를 더한 두 실행 모두 TPS·p95·p99·CPU 악화. 논리적으로 안전하다는 정적 검토와 실제 성능 이득은 별개 |

A는 제품 코드 2개와 테스트 1개다. 측정 실행 도구의 `--heap-mb` 옵션과 실제 노드 Heap 확인을 위한 Python 2개도 유지한다. 기존의 금융·복구·메모리 한도 코드는 이 결정 때문에 되돌리지 않았다.

## 같은 조건에서의 비교

- 직접 Aeron 요청이며 HTTP Gateway는 제외했다. Protobuf를 유지했다.
- 같은 Mac의 독립 Docker 노드 3개. 노드당 CPU 2개, 컨테이너 메모리 2 GiB, 최대 Heap 1,024 MiB. 세 노드의 실제 `MaxHeapSize`를 매번 확인했다. 클라이언트는 동일 Heap 설정 전달까지 확인했으며 실제 Heap을 별도로 조회하지 않았다.
- Archive sync는 세 노드 모두 `[2,2,2]`. BTC/SOL/SUI, 같은 사용자 자금을 사용한다.
- 접수 미응답 512개·금융 미완료 1,024개 상한, 비동기 ACK, 부분 체결 maker 워크로드.
- 매번 새 클러스터·불변 실행 이미지. 예열 20초, 측정 제출 10초, 해당 주문 전체 완료와 최종 ACK까지 확인했다. 더 긴 지속 시험을 추가하지 않았다.
- 단독 후보 16회, 조합 6회, 추가 직접 비교 6회로 총 **28회**. 계획과 순서, 이미지 식별자, 결과 원문을 보존했다.

세 노드 시험의 CPU/order와 B/order는 세 **서비스 스레드**의 구간 차분 합을 3과 주문 수로 나눈 노드 평균이다. 클러스터 전체 비용이나 클라이언트 비용이 아니다. 경계 CAPTURE 비용도 포함한다. 반복별 p99의 중앙값은 전체 지연 표본을 합친 p99가 아니다.

### 조합과 추가 비교

첫 조합 6회에서 후보별 반복 중앙값을 기준 반복 중앙값으로 나눈 변화율은 A+C의 TPS +1.82%, p99 **+8.36%**였다. A+B+C는 TPS **−7.16%**, p99 **+17.08%**, CPU/order **+8.11%**였다. 이는 비교 쌍별 변화율의 중앙값과 다른 집계다. 할당량만 줄었다고 모두 채택하지 않았다.

추가 직접 비교는 `기준 → C → A+C → A+C → C → 기준` 순서로 고정했다.

### 엔진 단독 진단

기존 엔진 실행기와 기존 반복 helper를 재사용했다. 기준/A 각각 새 JVM 3개에서 같은 작은 유한 워크로드를 5회 실행했다. 실행 전에 정한 집계는 각 JVM의 마지막 3회 중앙값, 이어서 JVM 3개의 중앙값이다. 초기 2회와 불리한 실행도 보존했다.

|---|---:|---:|

매 호출마다 상태를 새로 만든 짧은 진단이다. 지속 최대 TPS나 HTTP 처리량이 아니다. 마지막 A JVM의 다섯 번째 호출은 약 53,120 TPS로 낮았으므로 모든 실행이 개선됐다고 말하지 않는다. A의 채택 근거는 불필요한 소유 결과 복사 제거와 작은 할당량 감소이며, 처리량 수치를 보장하는 변경은 아니다.

앞서 같은 작은 워크로드를 새 JVM당 한 번씩만 실행한 각 3회는 기준 51,456 / 52,537 / 45,386 TPS, A 56,184 / 43,912 / 45,487 TPS로 혼재했다. 이 초기 결과도 `engine-runs.json`에 보존했다. 반복 진단의 예열된 값으로 이 결과를 덮어쓰거나, 서로 다른 집계를 같은 비교로 섞지 않는다.

## 정합성·복구 검증

28회 모두 같은 주문 집단에 대해 접수·실행 callback 수, 실제 잔고·예약·수수료·세 마켓 maker 잔량, admission 순번, 정확한 ACK floor를 대조했다. 최종 pending과 보관된 접수 결과는 0이며 세 노드의 상태 지문도 같았다. 별도 읽기 전용 검토가 84개 최종 노드 상태, 168개 시작/끝 checkpoint, 실행 이미지, 원본 성능 이벤트와 정리 원문을 다시 대조했다. 5,055개 대조 조건에서 불일치를 발견하지 못했다.

작성 대화를 상속하지 않은 별도 검토에서 A의 원본 명령 일치, 불변 이벤트 소유권, 결과 전체 검증, 반영 전 검증과 반영 중 실패 격리를 확인했다. B와 C의 제외 소스 파일이 기준과 같고, 최종 A 소스가 검토한 A 소스와 바이트 단위로 같음도 확인했다. 지연의 개별 표본 배열은 저장하지 않아 독립 검토가 percentile을 재산출하지는 못했으며, 산식·단위·원본 이벤트 일치까지 검토했다.

최종 선택한 소스의 회귀 결과는 다음과 같다. 모두 실패·오류·건너뜀 0이다. matching 156개와 trading 276개는 검증했던 A와 입력이 같아 Gradle의 `UP-TO-DATE` 결과를 재사용했다. architecture 385개와 app-api 70개, Python 13개 및 실제 장애·복구 2개는 이번 최종 검증에서 새로 실행했다.

변경 경로의 형식 검사와 공백 검사도 통과했다. 최초 A+B+C 조합의 회귀 894개도 통과했지만, 최종 887개와 중복 합산하지 않는다. 제외한 B/C 전용 테스트 7개도 최종 소스에서는 함께 복원했다.

실제 장애·복구 16개 조건:

1. 스냅샷 없는 genesis 로그만으로 전체 프로세스 재시작.
2. 리더 종료 후 같은 요청 재전송에서 중복 예약 방지.
3. 원래 볼륨을 유지한 follower 재합류.
4. 접수는 확정됐지만 실행 명령을 아직 보내지 않은 지점의 장애.
5. 일부만 기록된 스냅샷을 정상 복구 상태로 채택하지 않음.
6. 실행이 확정됐지만 접수 응답을 아직 전달하지 않은 지점의 장애.
7. 스냅샷과 확정된 후속 로그로 전체 재시작.
8. 과거 결과와 활성 maker가 재시작 후 유지됨.
9. 이전 MediaDriver 파일을 없앤 뒤 세 JVM 복구.
10. 스냅샷 root/실행 식별자가 다른 상태의 준비 완료 거절.
11. 별도 복구본의 필요한 기록 범위가 저장되기 전 접수 성공을 공개하지 않음.
12. 같은 기준으로 매칭·정산 완료 성공 공개를 제한함.
13. 원래 세 프로세스를 종료하고 원래 세 저장 폴더를 제거함.
14. 복구 권한을 한 번만 사용하며 같은 대상의 재시도는 안전함.
15. 남은 네 번째 복구본의 스냅샷·로그만으로 정확한 금융 상태 복원.
16. 과거 요청에 추가 예약이 생기지 않고, 남은 maker의 나중 체결도 정확함.

장애 시험은 Docker 성능 시험과 구분한 같은 Mac의 별도 JVM 시험이다. 네 번째 복구본도 같은 물리 컴퓨터에 있으므로 실제 별도 AZ·리전·스토리지 장애 영역을 검증한 것은 아니다. 과부하와 장애를 동시에 가한 장기 시험도 아니다.

별도 복구본 시험은 durability gate를 직접 기다려 저장 범위를 확인한다. 이 시험 하나로 실제 HTTP 응답 경로의 차단까지 검증한 것은 아니다. 장애 시험의 마지막에는 ACK하지 않은 접수 결과 4개가 남는 것이 정상이며, 최종 ACK 후 보관 결과가 0인 28회 성능 시험과 구분한다.

### 최종 소스와 시험 실행물 연결

최종 소스 595개가 저장된 manifest와 일치한다. 최종 재빌드 runtime은 A 성능 시험 runtime과 1,344개 파일 중 13개가 다르다. 제품 클래스 2개는 줄번호·SMAP만 다르고, 이를 정규화하면 opcode·상수·필드·메서드·예외·Kotlin metadata를 포함한 나머지 바이트가 같다. 나머지는 테스트 클래스이며 9개는 같은 종류의 디버그 정보 차이, 테스트 본체 2개는 기존 검증 강화 차이다. 성능 클라이언트 진입점 변경은 없다.

따라서 **거래 실행 동작은 같지만 실행물 전체 해시가 같다고 표현하지 않는다.** 실행 식별자가 전체 클래스 바이트를 포함하므로 최종 장애·복구 시험은 재빌드의 새로운 식별자로 실행했다. 원본 클래스·disassembly와 비교 결과도 보존했다.

## 근거 파일

`engineering/results/candidate-validation-20261031/`에 계획, 28회 전체 원본, 엔진 진단 전체 결과, 소스 snapshot·manifest, 최소 runtime overlay, 검증 로그를 보존한다. 중복된 전체 runtime 복사본과 시험용 이미지는 검증 뒤 제거한다. 이전 10분 37,691 TPS 결과는 이전 기준 제품의 결과로 계속 구분하며, 이번 A 변경의 지속 시험 결과로 옮겨 쓰지 않는다.

정리 완료: 매 실행 소유 컨테이너·세 기록볼륨·네트워크 정리, 시험 이미지 6개와 중복 runtime 5개 제거. 최소 overlay와 manifest를 먼저 확인한 뒤 복사본을 지웠으며 원래 기준 runtime과 작업 소스는 보존했다. 최종 점검에서 이번 노드·클라이언트 JVM과 `ha142-` 컨테이너는 없었다. 기존 다른 작업의 종료된 컨테이너는 건드리지 않았다. 근거 파일은 약 20 MiB이며, 종료 시 호스트 여유 공간은 약 77 GiB다.

보존한 원본은 성능 이벤트·명령 로그·금융 상태 캡처·검증 결과다. 시험에 사용한 Archive·기록 볼륨 전체를 보존한 것은 아니다.

현재 자료로 **안정적인 5만 TPS, sub-ms p99 또는 전체 최적화의 끝**을 입증하지 못했다. 이번 작업에서 남은 세 후보의 채택·제외는 모두 결정했으며 미검증 후보로 남기지 않는다.
