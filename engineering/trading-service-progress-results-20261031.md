## 용어부터 바로잡기

앞서 쓴 ‘비계측 단회 40,807 TPS’는 **JFR·외부 Java agent 같은 상세 추적을 끈 상태에서 한 번 측정한 값**이었다. TPS·응답·완료 시각 측정과 기존 운영 metric은 유지했다. 대표값이나 개선 입증 자료로 사용하기에는 부족했다. 그 단회와 이번 수정 후를 바로 비교하지 않고, 이번에 수정 전후를 모두 새로 반복 측정했다.

## 실제 코드 변경

| 변경 | 목적과 유지한 경계 |
|---|---|
| `DevelopmentFundingAdapter.idleForRetry` | 새로운 실행 전송·응답 전송의 첫 재시도에만 기존 cluster idle 상태를 reset한다. 이전 대기의 PARKING 상태를 바로 이어받는 일을 줄인다. 매번 reset하지 않으며, 기존 cluster idle의 background/interrupt 처리·시도/시간 한도·같은 바이트 재전송·양수 offer 확인·실패 처리·예약 유지도 보존한다. bounded 실행·기존 실행 claim·응답의 같은 원인 경로에 적용했다. |
| `TradingNodeMetricHandoff` | producer 전용 위치·slot index와 consumer 지역 위치·slot index를 사용한다. 매 표본마다 자기 atomic cursor를 다시 읽거나 `% capacity`를 계산하지 않는다. 상대 스레드에 공개하는 atomic prefix, 전체 duration 복사, producer 단일 소유, 포화·close·fatal·동기 fallback·drop 표시 및 기존 wakeup은 유지한다. |

금융 도메인·Protobuf·측정 클라이언트와 부하 종류는 바꾸지 않았다. Archive sync를 낮추거나 성공 응답의 기록 조건을 완화하지 않았다. worker park handshake는 메모리 순서와 별도 효과 검증이 필요해 이번에 넣지 않았다. Archive 1MiB 상한을 키우는 것도 관측 블록에 효과를 낼 근거가 없어 제외했다.

## 같은 조건에서 여섯 번 측정

기존 `ha-trading-probe.py`를 그대로 사용했다. 세 Docker 노드, Archive/catalog/Consensus sync=2, BTC/SOL/SUI partial-maker, Protobuf, 각 컨테이너 2CPU·2GiB 제한·Heap 최대1GiB, 접수 한도512·미완료 한도1024, 예열20초·제출10초다. 수정 전→후→후→전→전→후 순으로 새 클러스터를 실행했다.

JFR·외부 Java agent는 사용하지 않았다. 기존 운영 metric과 실제 응답·세 노드 완료 표식 수신은 그대로 측정했다. TPS 분모는 제출 창과 마지막 해당 cohort 관측을 포함한다. HTTP 및 원격 Backup 저장 확인은 제외다.

각 열의 중앙값은 서로 다른 실행에서 나올 수 있다. CPU·할당은 같은 노드의 전후 checkpoint 차분을 측정 주문 수로 나누고, 세 노드 평균을 구한 뒤 실행 중앙값을 냈다. 최종 CAPTURE·경계 제어 비용을 포함해 순수 금융 계산 CPU는 아니다. 실행 전송 phase는 비차단 offer와 재시도 idle을 포함하는 wall timer다.

완료 TPS 중앙값은 **8.1% 증가**, 완료 p99 중앙값은 **25.6% 감소**했다. 서비스 CPU는 세 비교 쌍 모두 감소했고 중앙값 감소는 6.1%였다. 할당은 거의 같다. 실행 전송 phase 경과는 세 쌍 모두 약68% 감소했다. 재시도 횟수가 적어진 것으로만 설명되는 결과는 아니며, 원래 대기 상태를 reset한 변경의 작동 근거와 맞는다. 두 코드 변경의 전체 성능 기여율을 각각 분리한 실험은 아니다.

## 왜 완료 선언을 여전히 제한하는가

실행 전송 phase와 서비스 CPU는 세 쌍에서 일관되게 줄었지만, 전체 p99는 모든 실행에서 개선되지 않았다. 기록·복제 확정과 FIFO 처리 자체를 제거한 변경은 아니며, 단일 Mac의 실행 환경도 안정적이지 않았다.

마지막 수정 후 실행 전후 host 전체에는 압축 해제 약19.37GiB·압축 약21.49GiB 상당, swap in103.55MiB·out1,047.75MiB가 발생했다. 이 범위에는 부팅·예열·10초 제출·최종 관측·정리가 모두 들어가며, 반복 페이지를 포함한다. 특정 callback을 swap에 직접 귀속하지 않으며 마지막 악화의 유일한 원인이라고 주장하지 않는다. 모든 실행의 동일 범위 카운터를 보존했다.

이번 판단은 **작은 진행 경로 개선은 채택하되, 성능 안정화 전체와 지속 최대 용량은 미완료**다. 메모리 압박이 큰 같은 환경에서 무작정 반복 측정하거나 수십 개 변경을 추가해 이 문제를 해결 완료로 포장하지 않는다. 다음 성능 검증에는 노드·발생기·호스트의 메모리 상주 예산을 맞추는 작업이 필요하다. 사용자 앱 종료나 Docker 전역 설정 변경은 이번에 하지 않았다.
