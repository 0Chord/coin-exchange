# #137 · 자금 리더 장애 뒤 최초 접수 결과와 예약 보존

**로컬 구현·검증 완료, 커밋·PR 전.** 작업 브랜치는 `test/funds-leader-failover/137`이다. 계약은 [이슈 #137](https://github.com/0Chord/coin-exchange/issues/137), 기준 코드는 통합 `26d2013cca94abcdc38a1a55c2d048a68ee7fc3b`다. #136의 9노드 실행·동일 Archive 복귀·전송 보류 도구를 재사용한다. 실제 과반 상실·네트워크 분할은 #138 범위이며 여기에는 포함하지 않는다.

## 확인할 흐름

사용 가능 자금1000에서 BTC 매수600을 예약한 직후 자금 리더를 종료한다. 남은 두 노드가 새 리더를 정한 뒤에도 사용 가능400·예약600과 최초 응답이 같아야 한다. 응답을 받지 못한 경우에도 같은 요청을 재전송해서 확인하며, 새 요청으로 바꾸거나 예약을 임의로 반환하지 않는다.

```text
BTC 전달 보류 설치 → 실제 자금 리더 확인 → B1 주문 접수·600 예약
                                                     │
                  ┌─ 실제 승인 응답 수신 ─────────────┤
                  └─ 실제 승인 응답을 시험 연결에서 숨김 ┤
                                                     ▼
                             그 자금 리더 종료 → 생존 두 노드의 새 임기
                                                     │
                                                     ▼
                  새 리더의 BTC 원본 전달 시도가 보류됐는지 확인
                                                     │
                                                     ▼
                     같은 B1 재확인 → 추가 예약 없이 최초 승인 반환
                                                     │
                                                     ▼
                           S1의500 요청 거절·최초 결과 보존
                                                     │
                                                     ▼
          보류 해제 → BTC 주문 대기 결과 → 자금 반영 → 매칭의 확인·회수
                                                     │
                                                     ▼
             구 리더 동일 Archive 복귀 → 새 S2 주문과 최초 거절 재확인
```

이번에는 상대 매도 주문을 넣지 않는다. ‘결과 반영 완료’는 미체결 주문이 주문장에 대기한다는 결과가 자금에 반영됐다는 의미다. 실제 체결 정산이나 자금 반환을 검증했다고 쓰지 않는다.

## 수기 기대값

가격100·수량 단위1·수수료0이다. 사용자 한 명, 요청 채널 두 개, 세대1을 유지한다. 최초 응답을 지우는 업무 ACK는 보내지 않는다.

| 지점 | 가용/예약 | 최초 응답·주문 상태 |
| --- | ---: | --- |
| 시작 |1000/0|요청 없음 |
| B1: BTC6 접수, 전달 보류 |400/600|최초 승인1, BTC 입력1, 아직 주문장에는 없음 |

같은 B1 번호에 수량7, 같은 S1 번호에 수량4를 보내면 내용 충돌이어야 한다. 수량4를 살 자금이 있더라도 기존 거절을 새 승인으로 바꾸지 않는다. 최종 예약700은 남은 주문의 담보이며 정상이다.

## 실제 장애와 응답 유실의 구분

- 성공 직후 종료는 실제 승인 응답을 받은 다음 업무 동작으로 그 응답을 만든 자금 리더를 종료한다. 종료 전 세 사본 수렴을 다시 기다려 장애 지점을 뒤로 미루지 않는다.
- 응답 유실은 실제 Aeron 연결에서 해석한 승인 응답을 보존한 뒤, 동기 client의 응답 처리 callback으로만 넘기지 않는다. 실제 응답 offer 직전 같은 서비스 소유 상태에서 buyer/USDT의 가용400·예약600을 복사한다. 서비스의 확정 처리 위치·원문·최초 응답·그 잔고·상위 미전달·전송 수용 후 client 미확인을 따로 대조한다. 단순 시간 초과나 offer 수용만으로 서버 접수를 주장하지 않는다.
- 새 리더 확인에는 생존 두 사본의 더 높은 임기·실제 리더 ID·현재 boot의 새 복제 probe가 필요하다. 죽은 노드의 옛 LEADER 파일은 선출 근거가 아니다.
- 새 자금 리더의 실제 전달 작업이 원래 B1을 보류 중에도 다시 시도해야 한다. 보류 해제 뒤 같은 원문을 실제로 전달하고 응답을 받은 작업까지 연결한다. 시험 코드가 수동 Apply/ACK로 진도를 대신 만들지 않는다.
- 구 리더 재기동은 시험 실행기가 명시적으로 수행한다. 같은 기록·주소·이미지·설정을 사용하고 그 노드의 boot만 달라진다. 자동 프로세스 재시작 정책을 검증한 것은 아니다.

## PR #187의 CI 중복 실행 수정

[Build and Test #256](https://github.com/0Chord/coin-exchange/actions/runs/43860084114)은 테스트 assertion 실패가 아니라 전체 작업의30분 한도 초과로 취소됐다. GitHub 주석의 원문은 `The job has exceeded the maximum execution time of 30m0s`다. 별도 **Architecture checks**는 구조 검사와 P01~P09 실행 확인을 이미 성공했지만, **Build and test**의 `build test --rerun`이 구조 검사를 다시 실행하다 취소됐다.

보관된 `test-reports` XML에는 제품·도메인1970개가 기록됐고 실패/오류0, 기존 skip3개다. 이번 #137 장애2개는 skip 없이 모두 통과했으며, 원격 실행의 최초 응답·400/600·새 리더·동일 기록 재합류·후속300/700·정리까지 성공했다. 기존 skip은 저장된 Archive 재생 입력 또는 별도 장애·복구 환경변수를 명시적으로 제공할 때만 실행하는 검사이며, 이 수정에서 새로 제외하거나 성공으로 세지 않는다. 원격 두 장애 run은 `multi1794830602566b14d8593`, `multi179483071998839657127`이다.

수정은 전체 빌드 명령에 `-x :architecture-tests:test`를 붙여 **이미 별도 필수 작업이 맡은 중복만 제거**한다. 구조 작업의 강제 실행·필수 보고·artifact, 제품·DB·Aeron 테스트와 패키징·린트는 유지한다. 두 필수 작업 이름과 전체30분·개별 run 한도도 바꾸지 않는다. 기본 로컬 `build`의 실행 범위는 그대로다.

YAML 구조와 기존 작업·보고서 설정을 대조했고, 실제 Gradle dry-run에서 제품 작업의8개 테스트 task와 구조 작업의1개 task가 각각 남는지 확인했다. dry-run은 작업 선택 검증이며 테스트 실행 성공으로 세지 않는다. 전체 `ktlintCheck`도 통과했다. 제품 코드·테스트는 기존 검증 이후 변경하지 않았으므로 동일한 실행 근거를 재사용하며, 수정된 원격 CI의 결과는 별도로 확인한다.

## PR #187의 제품 검사 실행 그룹 분리

중복 구조 검사를 제거한 뒤의 [두 번째 CI](https://github.com/0Chord/coin-exchange/actions/runs/43871256619)도 30분 작업 한도에 걸렸다. 이번에는 중복 구조 실행이 없었고, `app-api`의 여러 Docker 검증을 한 머신에서 직렬로 실행하던 중 취소됐다. 마지막 로그는 취소 흐름·복원 검증이 진행 중이었으며 `app-api` 최종 XML은 생성되지 않았다. 따라서 이 실행을 전체 제품 통과로 기록하지 않는다. 같은 테스트의 실행 시간도 이전보다 늘었지만, 공유 실행 머신의 CPU·디스크 중 무엇이 원인인지는 이 로그만으로 확정하지 않는다.

수정은 제품 검사를 아래 다섯 독립 머신에 배정한다. 같은 머신의 테스트 병렬도나 노드 메모리·복구 시간 제한은 늘리지 않는다. `Architecture checks`는 그대로 유지하고 `Build and test`는 모든 그룹 뒤의 필수 최종 관문으로 남긴다.

| 그룹 | 책임 | 기존 완료 XML 기준 사례 수 |
| --- | --- | ---: |
| general | 린트·전체 빌드·일반 앱·DB·도메인 | 1950 |
| transport | 복제·HTTP 접수·주문 전달의 무거운 검증 5클래스 | 5 |
| settlement | 결과 전달·취소·복합 복원 3클래스 | 9 |
| multi-market | 실제 9노드 공유 자금 검증 | 2 |
| failover | 매칭/자금 리더 장애 검증 | 4 |

이 표는 첫 CI의 기존 XML 1970사례를 새 배정에 대조한 기준이다. 기존 조건부 skip3개는 `general`에 남기고 통과와 별도 집계한다. 이전 XML의 재분류를 새 CI 실행으로 세지 않는다. 새 그룹의 실행과 최종 성공 여부는 해당 커밋의 원격 CI에서 별도로 확인한다.

배치표는 `.github/ci-test-groups.json` 하나다. 새 테스트는 기본 `general`이며, 명시된 클래스와 내부 클래스만 다른 그룹에 보낸다. `ciTestGroup`이 없는 기본 로컬 빌드에는 필터를 적용하지 않는다. 각 그룹은 전체 컴파일 후보와 실제 Gradle 선택 후보를 `ci-test-partition/inventory.json`에 기록한다. Gradle 성공 직후에는 실제 생성된 XML의 목록·지문을 `execution.json`에 고정해 artifact 전달 중의 누락·복제를 검사한다. 마지막 관문은 모든 그룹의 실제 성공을 먼저 요구하고, 동일 배치표·동일 전체 후보·그룹 간 중복 없는 합집합과 XML의 실패/오류·누락을 대조한다. 그룹 취소·실패·artifact 부재·실행0개·중복 결과·기존 조건부 3클래스 외의 skip은 실패다. 보고서는 `test-reports-그룹명`으로 나눠 7일 보관한다.

새 검증 스크립트의 준비·실행·검증문은 다음과 같다. 실제 거래 테스트를 대역으로 바꾸는 검사가 아니라 CI 분리·집계 도구 자체의 검사다.

| 준비(Given) | 실행(When) | 실제 확인(Then) |
| --- | --- | --- |
| 두 그룹의 후보·정상 XML·내부 클래스·새 클래스 | 배정/집계 실행 | 각 후보는 한 그룹이며 새 클래스는 general, 실제 결과 수 일치 |
| 중복 JSON 키·중복 클래스 배정·예약 그룹 이름·빈 그룹 | 배치표 읽기 | 명확한 오류로 거절 |
| 누락된 선택 후보·그룹 artifact·배정 클래스 XML | 집계 실행 | 누락 오류로 실패 |
| 다른 배치표 지문·전체 후보·추가 그룹 artifact | 집계 실행 | 실행 자료 불일치로 실패 |
| 실행 직후 고정한 XML을 누락·복제 | 집계 실행 | 목록·지문 또는 중복 결과 검사로 실패 |
| 다른 그룹의 결과·실패 결과·새 skip·전부 skip인 그룹 | 집계 실행 | 성공으로 집계하지 않고 실패 |
| 정상 사례와 기존 조건부 skip이 함께 있는 그룹 | 집계 실행 | 정상 통과와 skip을 분리해 집계 |

스크립트 자체 검사는 `.github/scripts/test_ci_test_groups.py`에 있고, 그룹별 실제 Gradle 후보 선택은 `:app-api:verifyCiTestPartition`으로 확인한다. 이 작업은 후보 선택 검사이며 제품 테스트 실행 성공을 대신하지 않는다.

로컬 새 `general` 실행은 전체 빌드·린트와 1950사례(앱1163·도메인787), 실패/오류0·기존 skip3으로 `BUILD SUCCESSFUL in 4m 21s`를 확인했다. 로그는 `/tmp/issue137-ci-general-verification.log`다. 실제 Gradle 후보는 전체604개에서 general583·transport5·settlement13·multi-market1·failover2로 중복 없이 나뉘며, 기본 실행은604개를 유지한다. helper·내부 클래스를 포함한 후보 수를 JUnit 사례 수로 세지 않는다. 알 수 없는 그룹은 실행 전에 거절됐다.

새 집계 스크립트의13개 검사는 통과했다. 기존 완료 XML224개를 새 실제 후보 배정과 재분류해 1970사례·통과1967·skip3 보존도 확인했으며, 이것은 새 클러스터 실행을 대신하는 근거가 아니다. 독립 리뷰가 찾은 개별 XML 누락·필수 클래스 skip·같은 그룹의 중복 결과는 실행 목록 고정·조건부 skip 구분·검사 식별자 중복 거절과 반례 검사로 보완했다. 원격 각 그룹과 최종 필수 관문의 결과는 해당 커밋의 CI에서 확인한다.
