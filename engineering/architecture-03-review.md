# ARCH-03 · HTTP 계층의 업무 우회를 막는 흐름

**로컬 구현·검증 완료. 구조 검사 196개 통과(ARCH-03 신규 37개 포함).** 기준 `b100276`, 브랜치 `test/http-entry-boundary/19`. 이 변경은 검사 도구·테스트·고의 정상/위반 예제다. 제품의 컨트롤러·유즈케이스·저장 코드는 변경하지 않았다. **ARCH-03은 예제 검증만 하며 실제 운영 적용은 #20–21에 남아 있다.**

이전에는 HTTP 역할과 의존 경계를 검사할 구현이 없었다. 이제 자료가 온전하면 HTTP 코드의 금지 의존을 보고하고, 대상이 빠지면 미평가로 멈춘다. [명세](architecture-check-spec.md)와 아래 세 흐름을 먼저 읽고 필요한 코드만 펼치면 된다. 이 작성 AI의 테스트 검토·구현 검증은 독립 리뷰나 사람의 검토 완료가 아니다.

## 전체 흐름과 읽기 순서

| 읽을 단위 | 입력 → 판단 → 결과 | 사람이 확인할 판단 |
| --- | --- | --- |
| 1. 검사 대상 준비 | 예제 출력·역할 목록 → 누락·충돌 확인 → 준비 완료 또는 미평가 | 빠진 코드를 통과로 표시하지 않는가 |
| 2. HTTP 의존 판단 | 준비된 HTTP 타입 → 허용·금지 대상 비교 → 위반 목록 | DTO 변환은 허용하고 업무 우회는 막는가 |
| 3. 숨은 참조와 보고 | 매퍼·부모·생성 코드·참조 위치 → 같은 경계 적용 → 실제 원인 위치 보고 | 변환 코드에 숨긴 저장 호출을 놓치거나 정상 유즈케이스 내부를 오탐하지 않는가 |

## 1. 검사할 대상이 모두 있는지 확인한다

**입력:** 컴파일된 예제 출력, HTTP 코드의 패키지 범위, 역할 목록, 필수 타입 목록. 역할은 ‘컨트롤러’, ‘변환’, ‘유즈케이스’, ‘데이터’, ‘저장 포트’ 같은 책임이다.

**정상:** 파일에서 발견한 컨트롤러·DTO가 실제로 읽혔고 역할도 하나씩 있다. 컨트롤러와 유즈케이스가 적어도 하나 있으며 API가 참조한 내부 타입의 정의·역할도 있다. 준비한 타입과 역할을 의존 검사로 전달한다.

**누락·충돌:** 여기서 등록은 Spring 등록이 아니라 검사기에 클래스의 역할을 알려주는 목록이다. 발견한 새 컨트롤러가 목록에 없으면 준비 오류다. 같은 `InputDto`를 ‘변환’과 ‘저장 포트’에 동시에 등록해도 오류다. 컨트롤러의 DTO 사용은 허용하지만 저장 포트 사용은 금지하므로, 검사기가 둘 중 하나를 임의로 골라서는 안 된다. 이는 DTO에서 저장 포트를 호출하는 코드 위반과 구분되는 검사 설정 오류다.

검사할 컴파일 결과물인 `.class` 파일이 빠지거나 손상돼도 준비 오류다. 가져온 목록이 파일에서 발견한 목록과 다르면 기존 수집기가 누락을 보고한다. 준비 과정에서 일부 타입·역할은 남을 수 있지만, 최종 검사기는 오류가 하나라도 있으면 **미평가·위반 목록 없음·검사 참조 수 0**으로 종료한다. 이것은 통과가 아니다. 이번 테스트는 이런 입력을 일부러 만든 예제이며, 제품에서 실제 누락·충돌을 발견했다는 뜻은 아니다.

**추가 보완:** 외부 `java.sql.Connection`을 허용 데이터 역할로 오등록하는 반례가 실패했다. 역할 등록은 지정한 프로젝트 범위의 타입만 받도록 보완했고, 명시한 금지 기술은 역할과 무관하게 금지하도록 했다.

읽을 코드: [준비 검증](../architecture-tests/src/test/kotlin/com/exchange/architecture/support/HttpBoundaryScope.kt), [기존 출력 수집](../architecture-tests/src/test/kotlin/com/exchange/architecture/support/ProductionScopeImporter.kt). 테스트: [역할·누락](../architecture-tests/src/test/kotlin/com/exchange/architecture/HttpBoundaryScopeTest.kt), [실제 출력 파일과 연결](../architecture-tests/src/test/kotlin/com/exchange/architecture/HttpBoundaryImportTest.kt).

**읽기 힌트:** `object HttpBoundaryScope`는 상태를 저장하는 거래 객체가 아니라 검사 함수를 모아 둔 Kotlin 객체다. `prepare`가 오류 목록을 반환하고, 다음 `inspect`가 그 목록을 확인해 평가 진행 여부를 결정한다.

## 2. HTTP 코드가 누구를 사용하는지 검사한다

**입력:** 준비 오류가 없는 클래스와 역할 목록. 출발점은 컨트롤러와 DTO·매퍼 등 변환 코드다. 일반 유즈케이스·저장 구현은 이 규칙의 출발점으로 잡지 않는다.

| 코드에서 확인한 관계 | 결과와 이유 |
| --- | --- |
| 컨트롤러 → 등록한 유즈케이스, 값 객체·명령 생성, 응답 DTO 구성 | 허용. `Service`라는 이름의 진입점도 역할이 맞으면 허용 |
| 컨트롤러 → Store, 구현체, Repository, 영속 객체 | 위반. 인터페이스이거나 아직 사용하지 않는 주입이어도 금지 |
| 컨트롤러 → 내부 예약·정산, Coordinator·엔진·실행기·주문장 | 위반. 이름을 UseCase로 바꾸기만 해도 금지 역할은 그대로 |
| 유즈케이스 → 내부 작업·저장 포트 | HTTP 규칙의 검사 출발점이 아님. 업무 조율에 필요한 의존을 컨트롤러의 직접 저장 접근으로 보지 않음 |
| 컨트롤러 → 실제 웹 매핑·응답 타입 | 허용. Spring 전체를 금지하지 않음 |
| 컨트롤러 → 명시된 JDBC/JPA·외부 HTTP 클라이언트 | 위반. Spring Web 패키지 전체를 허용하지 않음 |

검사는 실제 코드의 직접 참조를 읽는다. 생성자 주입·필드·인자·반환·배열·제네릭·상속·어노테이션에도 금지 타입이 있으면 위반이다. 클래스 이름의 접미사만 보고 판정하지 않는다.

예를 들어 `컨트롤러 → 유즈케이스 → 저장 포트`에서 ARCH-03은 첫 관계를 허용하고, `컨트롤러 → 저장 포트`는 거절한다. HTTP 출발점의 직접 참조를 보므로 유즈케이스 본문까지 같은 금지 기준을 확장하지 않는다. 유즈케이스가 구체 DB 구현을 참조해도 되는지, 도메인의 판단을 대신하고 있는지는 별도의 애플리케이션 의존·책임 기준으로 확인할 내용이다. ARCH-03 통과는 유즈케이스 내부 전체가 올바르다는 보장이 아니다.

읽을 코드: [의존 판정과 결과](../architecture-tests/src/test/kotlin/com/exchange/architecture/rules/HttpEntryBoundary.kt). 테스트: [정상·위반 계약](../architecture-tests/src/test/kotlin/com/exchange/architecture/HttpEntryBoundaryContractTest.kt).

**읽기 힌트:** `HttpBoundaryResult.evaluated`가 먼저다. 이것이 `false`면 `violations`가 비어 있어도 통과로 읽으면 안 된다. `referenceCount`는 읽은 직접 참조의 수이며 실행한 업무의 수가 아니다.

## 3. 숨은 참조와 보고의 정확성을 확인한다

컨트롤러가 매퍼만 호출해도 매퍼 내부에서 저장소를 쓰면 **매퍼의 위반**으로 보고한다. DTO 메서드와 최상위 확장 함수도 같은 규칙을 받는다. Kotlin 최상위 함수는 컴파일된 파일 파사드에 들어가므로 그 클래스도 역할 목록에 등록한다.

공통 컨트롤러 부모의 사용 자체는 허용하지만 부모 안의 저장 호출은 별도 출발 타입으로 검사한다. 중첩·익명 클래스는 실제 포함 관계로 소유 역할을 이어받는다. 람다·메서드 참조가 남긴 바이트코드를 읽으며 이름에 `$`가 있다는 이유로 버리지 않는다.

**정확한 위치:** 확장 함수의 저장 호출은 `MappingFunctions.kt`의 7행으로 검증한다. 반환 타입처럼 행 정보가 없는 참조는 `null`로 남긴다. 다른 타입의 행을 만들어 붙이지 않는다. 동일 근거는 중복을 제거하고 입력 순서가 달라도 같은 진단으로 정렬한다. 주입과 실제 호출은 서로 다른 근거로 유지한다.

Kotlin 메서드 참조는 컴파일 시 별도 클래스의 호출이 될 수 있다. 해당 호출이 실제로 존재하는지 확인하고 검사했다. 작은 Java 예제도 별도로 두어 JVM 메서드·생성자 참조의 실제 위치(12·16·20행)를 확인했다. 예제의 `save`는 거래 저장 기능이 아니며 테스트는 그 업무 메서드를 실행하지 않는다.

예제 코드: [입력·계약 역할](../architecture-tests/src/test/kotlin/com/exchange/architecture/fixtures/httpboundary/Contracts.kt), [HTTP 정상·고의 위반](../architecture-tests/src/test/kotlin/com/exchange/architecture/fixtures/httpboundary/web/HttpFixtures.kt), [확장 함수의 위반](../architecture-tests/src/test/kotlin/com/exchange/architecture/fixtures/httpboundary/web/MappingFunctions.kt), [JVM 참조](../architecture-tests/src/test/java/com/exchange/architecture/fixtures/httpboundary/web/JavaReferenceController.java).

## 사례와 검증 근거

위반 예제를 정확히 잡으면 테스트는 통과한다. 제품에 위반을 추가했다는 뜻이 아니다. 기대값은 C06과 명세의 역할별 허용 표에서 정했고, 검사기의 실제 결과를 정답으로 복사하지 않았다.

| 명세 사례 | 테스트가 확인한 것 |
| --- | --- |
| HTTP-01~03 | 정상 입력·응답 변환, Service 이름/인터페이스 진입점, 실제 Spring 웹 지원 |
| HTTP-04~06 | 포트·구현·영속 객체·내부 작업 금지, 타입만 보유한 경우와 참조 형태 |
| HTTP-07~08 | Kotlin/JVM 메서드·생성자 참조, 매퍼·DTO·확장 함수·부모의 우회 |
| HTTP-09~11 | 유즈케이스 내부는 검사 끝 경계, 변환 책임 초과와 외부 기술 금지 |
| HTTP-12~14 | 빈 역할, 미등록/충돌, 출력 누락·중복·손상·읽기 실패, 실제 수집 연결 |
| HTTP-15~16 | 중첩·람다·익명 타입, 정렬·중복 제거, 위치 부재, 준비 실패 시 부분 위반 억제 |

테스트 검토에서는 위반 여부만이 아니라 **출발·금지 대상 쌍과 정확한 오류 종류·대상**을 대조했다. 정상 허용 사례를 함께 두어 전부 거절하는 구현도 통과하지 못하게 했다. 위치 고정값은 실제 예제 소스와 바이트코드 사전 조건을 확인해 정했다.

## 실제 실행 상태

- 대상 준비: 첫 6개 모두 어설션 실패 → 구현 후 6개 통과.
- 기본 판정: 4개 중 3개 실패·1개 허용 사례 통과 → 구현 후 대상 준비 포함 10개 통과.
- 참조 형태·우회: 23개 집중 검사 통과. 기존 기본 구현이 이미 충족한 사례에는 인위적인 Red를 만들지 않았다.
- 실제 출력·등록 보완: 36개 중 외부 타입 오등록 반례 1개 실패 → 수정과 JVM 참조 사례 추가 후 **37개 집중 검사 통과**.
- JDBC 구체 타입 등 외부 기술 예제 보강 후 `:architecture-tests:test --rerun-tasks`: **196개 실제 실행, 실패·오류·skip 0**.
- 독립 명령 dry-run: 다른 제품 모듈 test 작업이 선행에 없음.
- `build --no-daemon --continue`: 성공, **30개 작업 UP-TO-DATE**. 제품 테스트의 새 전체 실행 결과로 세지 않는다.

[명령·결과·소스 해시 기록](architecture-03-verification.json)을 현재 코드와 대조할 수 있다.

위 실행 기록은 PR 게시 전 로컬 스냅샷의 결과다. 원격 CI와 독립 리뷰 상태는 해당 PR에서 확인한다. 코드·테스트와 자기 검토를 연결했으며, 사용자 이해나 승인 완료로 기록하지 않는다.

**남은 경계:** ARCH-03은 프로젝트 내부 역할과 명시한 외부 기술의 직접 참조를 검사한다. 등록한 데이터 타입 안의 의미적 업무 판단, 모든 외부 I/O, 동적 로딩·프록시의 실제 대상, HTTP 응답/호출 횟수·순서, DB·동시성·롤백은 보장하지 않는다. 실제 운영 목록·패키지 연결은 #20, 저장 경계 이동 후 유지는 #21이다. ARCH-04·05 및 #19 전체는 완료하지 않았다.
