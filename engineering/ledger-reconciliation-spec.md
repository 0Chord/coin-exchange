# #74 원장으로 계산한 돈과 실제 잔고가 같은지 확인하기

**실행 범위 확정 · 제품 코드와 테스트는 아직 작성하지 않았다.** #74는 내부 유즈케이스와 실제 DB 테스트로 검증한다. HTTP 조회 API는 제외하고, 복구 후 거래 재개 판단 연결은 #58에서 진행한다. 기준은 PR #80이 병합된 통합 브랜치 `eecbf481c75fbdcdb64b73234fa7ab3ceec2bafe`다. 선행 #43·71·72·73의 저장 계약을 유지한다.

## 1. 이번에 만들 결과

**원장 기록으로 계산한 잔고와 DB 잔고를 비교한다. 다르면 사용자·자산·사용 가능 금액 또는 예약 금액별로 차이를 보여준다. 잔고는 자동으로 수정하지 않는다.**

예를 들어 철수의 원화 사용 가능 금액이 원장 기록으로는 900원인데 DB에는 901원으로 저장돼 있다면, **“철수의 원화 사용 가능 잔고가 기록보다 1원 많다”**고 알려준다. 주문에 묶인 예약 금액도 별도로 비교한다.

수수료 없는 BUY 주문의 예다. 처음 가진 1,000에서 300을 예약하고, 100만 체결한 뒤 남은 200을 취소한다.

| 확인할 때 | 사용 가능한 돈 available | 주문에 묶인 돈 hold | 아직 활성인 예약의 합계 |
| --- | ---: | ---: | ---: |
| 처음 | 1,000 | 0 | 0 |
| 300 예약 직후 | 700 | 300 | 300 |
| 100 체결 후 | 700 | 200 | 200 |
| 남은 200 취소 후 | 900 | 0 | 0 |

각 시점에 **원장 합계와 DB 값이 각각 같아야 한다.** available와 hold를 합쳐 총액만 비교하면 안 된다. 취소 뒤 DB available만 901이면 “원장 900 / DB 901 / DB가 1 많음”으로 보고한다.

## 2. 확정한 실행 범위와 문답

**질문:** 이 결과를 어디서 확인할까?

- **AI 추천 · 채택:** 내부 유즈케이스와 실제 DB 테스트의 결과로 먼저 확인한다. HTTP 조회 API는 만들지 않고, 이후 #58에서 복구 후 재개 판단에 연결한다.
- **검토한 대안 · 이번 범위 제외:** 이번에 읽기 전용 HTTP 조회 API도 만든다. 접근 권한·응답 계약·실제 서버 요청 테스트까지 범위가 늘어난다.

**실제 사용자 답변:** “내부 유즈케이스와 실제 DB 테스트의 결과로 먼저 확인한다. HTTP 조회 API는 만들지 않고, 이후 #58에서 복구 후 재개 판단에 연결한다. 이거로 먼저 해 나중에 한번에 복구 후 재개 판단에서 연결하는게 나을 것 같아.”

**결정 · 확정:** 이번에는 내부 호출과 실제 DB 검증까지 만든다. 사용자가 말한 이유대로 복구 후 재개 판단 연결은 #58에서 함께 다룬다. API·접근 권한·HTTP 응답/네트워크 테스트는 #74의 완료 조건에 넣지 않는다. 외부에서 직접 대조 결과를 조회할 요구가 생기면 API 범위를 별도로 검토한다.

## 3. 입력 → 읽기 → 계산 → 결과

1. 호출자가 **마켓 ID와 그 마켓의 두 자산 ID**를 넘긴다. 빈 범위·같은 자산 두 번·전체 자산을 뜻하는 와일드카드는 허용하지 않는다. 사용자 한 명만 골라 누락을 가리는 검사도 만들지 않는다.
2. 저장 구현이 한 읽기 전용 DB 트랜잭션에서 원장·잔고·예약을 읽는다. 중간에 다른 거래가 완료돼도 조회들을 같은 DB 시점으로 묶는다.
3. 순수 Kotlin 객체가 사용자·자산별 원장 available/hold를 계산한다. **사용자 원장 합계는 CREDIT 합계 − DEBIT 합계**다. KRW와 BTC는 별개다.
4. 원장·잔고·예약 중 한 곳에라도 등장한 사용자·자산을 모두 검사한다. 활성 예약의 `remainingAmount`도 사용자·자산별로 더한다.
5. 원장 available ↔ DB available, 원장 hold ↔ DB hold, 활성 예약 합계 ↔ DB hold를 각각 비교한다. 누락 행·잘못된 기록은 별도로 표시한다.
6. 아래 네 결과 중 하나와 검사 범위·대상 수·구체적인 차이를 반환한다. 보고서 때문에 별도 DB 기록을 쓰지 않는다.

| 결과 | 뜻 | 사람이 할 일 |
| --- | --- | --- |
| 일치 `MATCHED` | 읽은 범위의 세 비교와 기록 검증이 모두 통과 | 범위와 제외 사항을 확인한다. 거래 재개를 자동 승인하지 않는다 |
| 불일치 `MISMATCHED` | 금액 차이, 필요한 행 누락 또는 읽을 수 있는 기록의 이상 | 사용자·자산·항목·원본 기록을 확인한다. 자동 보정하지 않는다 |
| 검증 불가 `UNAVAILABLE` | DB 읽기/트랜잭션 실패 또는 단일 마켓 검사 전제를 만족하지 못함 | 실패 이유를 먼저 확인한다. 부분 결과를 일치로 보지 않는다 |
| 대상 없음 `EMPTY` | 선택한 범위에 원장·잔고·예약 근거가 모두 없음 | 아무것도 비교하지 않았음을 확인한다. “일치”와 구분한다 |

**DB 0 잔고 행이 있으면 대상 없음이 아니다.** 해당 행을 실제로 검사해 일치로 보고하고 대상 수에 포함한다.

## 4. 한 시점으로 읽는 경계

**추천 구현:** 기존 `TransactionTemplate`·트랜잭션 관리자·JDBC를 재사용하고, 저장 구현이 `REPEATABLE_READ` 읽기 전용 트랜잭션을 소유한다. 이미 실행 중인 외부 트랜잭션 안에서 호출하면 거절한다. 외부의 낮은 격리 수준에 조용히 합류하지 않는다. 별도 `REQUIRES_NEW` 연결과 실행기를 추가하지 않는다.

PostgreSQL의 기본 격리 수준에서는 같은 트랜잭션의 연속 SELECT도 서로 다른 시점을 읽을 수 있다. `REPEATABLE_READ`는 첫 데이터 조회에서 정해진 스냅샷을 이후 조회도 사용한다. 이것이 이번 읽기 경계의 근거다. [PostgreSQL 16 격리 수준](https://www.postgresql.org/docs/16/transaction-iso.html), [Spring의 외부 트랜잭션 합류 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)

Spring의 readOnly 설정만으로 모든 쓰기 금지를 증명했다고 보지 않는다. 같은 연결에서 PostgreSQL 읽기 전용 모드까지 설정하고 실제 DB 테스트에서 `transaction_isolation=repeatable read`, `transaction_read_only=on`을 확인한다. SELECT FOR UPDATE나 행 잠금으로 거래를 멈추지 않는다. [PostgreSQL 읽기 전용 트랜잭션](https://www.postgresql.org/docs/16/sql-set-transaction.html)

조회 결과는 호출 시점에 이미 커밋된 DB 기록의 대조다. 실행 중인 매칭 엔진의 상태, 앞뒤의 모든 HTTP 처리, 이후 쓰기까지 한 번에 고정하는 기능은 아니다. 보고서 생성 시각을 DB 스냅샷의 정확한 커밋 시각이라고 표시하지 않는다.

## 5. 빠진 데이터를 숨기지 않는 계산 규칙

| 항목 | 이번 계약 |
| --- | --- |
| 읽을 원장 | 개시부터 저장된 기록. OPENING·RESERVE·RELEASE·SETTLEMENT를 포함하고, 존재하는 REVERSAL도 같은 분개 규칙으로 포함한다. 사건 시각이나 최근 날짜로 잘라 합산하지 않는다 |
| 원장 거래의 완전성 | 거래 머리글과 분개를 함께 읽는다. INNER JOIN으로 분개 없는 머리글을 지우지 않는다. 양수 금액·알려진 방향·자산별 차변/대변 균형을 확인한다. 잘못된 거래를 제외한 나머지만으로 일치라고 하지 않는다 |
| 시스템 계정 | DEVELOPMENT_FUNDING·FEE_REVENUE 항목도 거래의 균형 검증에 포함한다. 사용자 DB 잔고와 비교하거나 사용자와 같은 증가 방향으로 일반화하지 않는다 |
| 사용자 계정 해석 | `USER:<userId>:<assetId>:AVAILABLE/HOLD`를 해당 분개의 자산 ID와 함께 해석한다. 대소문자를 바꾸지 않는다. 무조건 `:`로 네 조각을 만들거나 새 거래 ID 제약을 추가하지 않는다. 식별이 불가능하거나 계정의 자산과 분개 자산이 다르면 기록 이상이다 |
| 검사 대상 | 원장 사용자 계정 ∪ DB 잔고 ∪ 관련 예약의 사용자·자산. 잔고가 있는 행만 기준으로 JOIN해 나머지를 없애지 않는다 |
| 없는 금액과 없는 행 | 한 계정의 분개 없음은 계산상 0이다. 하지만 원장/예약 근거가 있는데 필요한 DB 잔고 행이 없으면 행 누락이다. 0으로 대체해 일치시키지 않는다. 원장 없는 DB available/hold=0 준비 행은 정상이다 |
| 예약 합계 | 해당 마켓의 ACTIVE 예약 `remainingAmount`만 합산한다. 이 값에 남은 수수료 예약도 포함되므로 `remainingFeeReserveAmount`를 한 번 더 더하지 않는다. SETTLED·RELEASED는 활성 합계에 넣지 않는다 |
| 자산·범위 | 지정된 두 자산의 사용자 금액을 검사한다. 잔고는 마켓별로 분리돼 있지 않으므로, 같은 자산의 다른 마켓 ACTIVE 예약을 발견하면 범위 미지원으로 검증 불가다. 이를 무시하고 hold가 맞는다고 하지 않는다. 현재 다른 목적의 hold는 없다는 전제를 명시한다 |
| 큰 합계 | 원장·예약 합계와 차이는 BigInteger로 정확히 계산한다. 개별 DB 금액은 기존 Long을 유지한다. 합계가 Long 범위를 넘어도 잘라 쓰거나 0으로 돌리지 않는다 |
| 읽기 실패 | 연결 실패·SQL 실패·트랜잭션 완료 실패는 검증 불가와 실패 단계/원인을 남긴다. 조회 실패를 빈 목록으로 바꾸지 않는다. 프로그래밍 오류까지 무조건 삼켜 정상 결과로 만들지 않는다 |

**차이의 방향은 `실제 DB 값 − 비교 기준값`으로 통일한다.** 예: 원장 900, DB 901이면 +1. 예약 비교는 예약 합계가 기준값이다. 누락 행이나 계산할 수 없는 손상에는 금액 0을 꾸며 넣지 않고 “값 없음/계산 불가”와 원본 식별자를 남긴다.

결과에는 범위, 읽기 완료 여부, 대상 수, 사용자·자산별 세 비교, 차이 목록을 담는다. 같은 입력을 사람이 따라 읽을 수 있도록 사용자·자산·항목 기준으로 정렬한다. 새 모니터링 플랫폼이나 범용 규칙 프레임워크는 만들지 않는다.

## 6. 현재 있는 코드와 추가할 코드

**확인한 사실:** 현재 `LedgerTransactionStore`는 원장 추가와 원본 사건 ID 조회만 제공한다. 전체 원장·잔고·예약을 한 스냅샷으로 대조하는 유즈케이스는 없다. 기존 금전 이동 SQL과 #71~73의 원자 저장 경계는 이번 변경 대상이 아니다.

아래 이름은 **신규 파일 제안**이다. 정확한 보조 DTO 개수나 모든 함수 본문을 미리 고정하지 않는다.

| 역할 | 제안 이름과 위치 | 맡을 일 |
| --- | --- | --- |
| 호출 진입점 | `ReconcileLedgerUseCase` · app-api의 `com.exchange.core.api.ledger.application` | 범위를 받고 완전한 스냅샷을 요청한 뒤 계산 결과를 반환한다. 쓰기 서비스는 호출하지 않는다 |
| 외부 읽기 계약 | `LedgerReconciliationStore` · domain-ledger의 `com.exchange.core.ledger` | 한 번의 호출에서 완전한 읽기 결과를 제공하는 포트. JDBC·Spring·OrderReservation 타입은 노출하지 않는다 |
| 실제 DB 읽기 | `PostgresLedgerReconciliationStore` · app-api의 `com.exchange.core.api.ledger.infrastructure.persistence` | 트랜잭션 경계를 소유하고 원장·잔고·예약 조회를 수행한다. 예약은 비교에 필요한 키·상태·금액으로 전달한다 |
| 순수 판단 | `LedgerReconciliation` · domain-ledger의 `com.exchange.core.ledger` | 전달받은 기록만으로 합산·대조한다. DB를 호출하지 않는다. 단순한 불변 입력/결과를 사용한다 |
| Bean 조립 | 기존 `LedgerPersistenceConfig` · `com.exchange.core.api.config` | 영속화 enabled 설정 아래 포트 구현과 유즈케이스를 `@Bean`으로 연결한다. `@Service`·`@Component`는 추가하지 않는다 |

domain-ledger → domain-order 의존은 추가하지 않는다. 이미 합의한 ledger application/persistence/core 폴더를 사용한다. 클래스별 역할 등록이나 새로운 허용 폴더도 필요 없다. 영속화가 꺼진 구성에 “항상 일치”하는 NoOp 검사 Bean을 넣지 않는다.

DB에서는 원장 머리글·분개를 누락 없이 읽고, 잔고·예약은 두 자산 범위로 읽는다. 머리글만 있는 거래도 발견해야 하므로 현재 작은 개발 DB에서는 머리글을 먼저 누락 없이 확인하는 방식을 우선한다. 원장 거래의 균형은 사용자 항목만이 아닌 전체 항목으로 확인한다. 원본 사건 ID마다 개별 조회를 반복하는 N+1 방식은 피한다. 대량 운영 데이터의 페이지 조회·증분 집계는 후속이다.

## 7. 정상·차이·누락·실패 사례

테스트의 기대값은 아래 독립 숫자에서 정한다. 구현한 합계 함수를 다시 호출해 기대값을 만들지 않는다. **표는 검증 계획이며 통과 결과가 아니다.**

| 사례 | 준비와 실행 | 기대 결과와 근거 |
| --- | --- | --- |
| A1 예약 직후 | OPENING 1,000 → 실제 예약 서비스로 300 예약 → 대조 | 일치. available 700 / hold 300 / 활성 예약 300 |
| A2 부분 체결·취소 | BUY 3개×100, 그중 1개 체결, 남은 2개 취소. 상대의 자산과 개시 기록도 준비 | 일치. 구매자 결제 자산 available 900 / hold 0 / 활성 예약 0. 받은 자산 1은 그 자산에서 별도로 비교 |
| A3 수수료·가격 개선 | 구매자 KRW 개시 1,000,000, 판매자 BTC 개시 10. BUY 2×100,000, 수수료 예약 2,000. 실제 2×90,000 체결, 구매 수수료 1,800·판매 수수료 900 | 구매자 KRW 818,200·BTC 2, 판매자 BTC 8·KRW 179,100, hold 모두 0. SYSTEM KRW 수익 2,700도 거래 균형에 포함. 기존 정산 경로를 재사용하되 개시·예약 원장을 빠짐없이 준비 |
| B1 잔고만 +1 | A2 후 DB available만 901로 손상 | 불일치. 원장 900 / DB 901 / 차이 +1. 호출 전후 돈과 기록은 그대로 |
| B2 총액 같지만 잘못 분류 | A1 후 DB 800/200으로 손상. 전체 1,000은 그대로 | available +100, hold −100, 예약 대비 hold −100을 각각 보고 |
| B3 hold 부족·초과 | A1의 예약 300을 유지하고 hold를 299 또는 301로 손상 | 각각 −1 또는 +1. 사용자 합계나 다른 자산의 값으로 상쇄하지 않는다 |
| B4 빠진 행 | 원장만 남은 비영 금액, 잔고 행 삭제, 예약만 존재하는 고아 사용자 | 합집합에 포함해 누락/차이를 보고. 존재하지 않는 행을 0 행처럼 통과시키지 않는다 |
| B5 원장 누락·중복 효과 | A2의 RELEASE를 삭제하거나 다른 원본 ID로 동일한 반환 분개를 한 번 더 저장 | 정상 DB 900/0과 대조 시 누락은 원장 700/200, 중복은 1,100/−200이므로 차이를 보고. 남은 기록으로 계산한다. 같은 ID 중복은 기존 고유 제약에 맡긴다 |
| B6 손상된 원장 | 머리글만 남음, 분개 한 개 삭제, 계정/자산 불일치 등 | 원본 거래/분개와 이상 종류를 보고하고 전체 일치를 금지한다. 손상 자료를 제외한 합계로 통과시키지 않는다 |
| E1 빈 범위 | 관련 기록·잔고·예약이 모두 없음 | 대상 없음. 다른 자산에만 데이터가 있으면 이 범위에는 여전히 대상 없음이며 전체 DB 정상이라고 말하지 않는다 |
| E2 준비한 0 잔고 | available/hold 0인 수취 잔고 행만 있음, 분개 없음 | 일치, 실제 검사 대상 1개. 금액 0과 조회 미실행을 구분 |
| E3 큰 합계·여러 자산 | Long 최대에 가까운 양수 분개들을 합산하고 반대 분개로 상쇄하는 자료, 서로 다른 두 자산 | BigInteger로 정확히 대조. 자산별로 각각 차이를 보고하고 서로 상쇄하지 않는다 |
| F1 동시 쓰기 | 대조가 첫 SELECT 후 대기하는 동안 실제 예약 서비스가 300을 커밋하고, 이후 대조를 계속함 | 첫 대조는 개시 1,000/0/0으로 일치. 다음 대조는 700/300/300으로 일치. 중간 혼합값은 금지 |
| F2 DB 실패·잘못된 호출 | 조회 도중 SQL/연결 실패, 이미 열린 외부 트랜잭션에서 호출, 같은 자산의 다른 마켓 ACTIVE 예약 | 검증 불가. 읽기 실패/호출 경계/범위 미지원 원인을 구분하고 자동 수정이나 재개는 없음 |

A3의 숫자: 실제 거래 대금 180,000, 구매 수수료 1,800, 예약 반환 20,200이다. 따라서 구매자 KRW는 1,000,000−180,000−1,800=818,200. 판매자는 180,000−900=179,100이다. 이 기대값은 검사기나 수수료 계산기를 호출해서 생성하지 않는다.

F1은 두 실제 DB 연결과 명시적인 동기화 지점으로 확인한다. sleep 시간이나 우연한 스레드 순서로 성공을 주장하지 않는다. 장애·손상용 SQL은 테스트 준비에서만 사용한다. 실제 검사 코드는 SELECT와 트랜잭션 제어만 수행해야 한다.

## 8. 한 PR 안에서 읽고 검증할 세 단위

1. **숫자를 비교하는 순수 객체:** A1/A2 숫자, B1/B2/B4, E1/E2/E3을 불변 입력으로 검증한다. 입력이 들어오면 어떤 합계를 만들고 차이를 내는지 먼저 읽는다.
2. **실제 DB에서 같은 시점의 자료 읽기:** 기존 PostgreSQL/Testcontainers를 사용해 A1/A2/A3·B5/B6·F1/F2를 확인한다. 첫 조회와 후속 조회가 같은 시점인지, 누락을 읽어냈는지 확인한다.
3. **Bean과 결과 전달 연결:** 실제 유즈케이스·저장 구현·기존 자금 이동 서비스를 연결한다. 원본 데이터가 검사 전후 같고, 불일치와 검증 불가를 구분해 사람이 읽을 수 있는 테스트 결과에 남기는지 확인한다.

첫 구현 단위는 **A1의 700/300/300이 일치하고, 같은 입력의 DB available만 701이면 +1 차이가 나오는 순수 비교**다. 프레임워크나 전체 복구 흐름부터 만들지 않는다. 구현 전 테스트 작성 → 기대값 검토 → 구현 → 실제 DB 검증을 연결한다.

주 협력 객체는 실제 구현을 사용한다. 이번에는 내부 유즈케이스와 PostgreSQL/Testcontainers로 검증하고, HTTP API·MockMvc·네트워크 테스트는 추가하지 않는다. 향후 실제 HTTP 시나리오는 #81의 테스트 방향에 연결한다. 범용 UI·별도 보고서 생성 도구는 추가하지 않는다. 기존 Gradle 테스트 HTML/XML과 흐름 설명을 재사용한다.

**후속 구현 시 예상 검증 명령** — 현재는 신규 테스트가 존재하지 않으므로 실행 결과로 표시하지 않는다. 아래 작업 폴더에서 테스트를 추가한 뒤 실제 이름과 결과를 기록한다.

```bash
cd /Users/0chord/.codex/worktrees/issue74-ledger-reconciliation/exchange-core
./gradlew :domain-ledger:test :app-api:test :architecture-tests:verifyArchitectureReport ktlintCheck
```

검사 명령이 성공했다는 사실과 세 비교의 실제 assertion이 통과했다는 사실을 연결한다. 기존 CI를 재사용하고 새 job이나 다른 구현 언어는 추가하지 않는다. 전체 테스트 범위가 커서 반복 비용이 크면 작성 중에는 새 테스트로 한정하고 마지막에 관련 회귀 범위를 기록한다.

## 9. 완료 기준과 보장하지 않는 것

- [ ] 네 결과와 차이의 방향, 한쪽에만 있는 대상·빈 대상·0 잔고의 처리가 설명과 실제 결과에서 일치한다.
- [ ] 개시·예약·기존 정산·취소 반환의 실제 DB 사례와 수수료/가격 개선 사례가 원장·잔고·예약을 빠짐없이 비교한다.
- [ ] 누락·손상·큰 합계·동시 쓰기·DB 오류 사례가 거짓 일치를 막는다. 외부 트랜잭션 합류와 읽기 전용 경계를 실제 DB로 확인한다.
- [ ] 검사 전후 원장·잔고·예약은 바뀌지 않는다. 새 writes, 행 잠금, NoOp 일치 결과가 없다.
- [ ] 기존 모듈 방향·폴더·Bean 조립과 기존 금전 이동 SQL·트랜잭션을 유지한다. 필요한 주석은 이유/경계를 한국어로 남긴다.
- [ ] 실제 코드·테스트를 연결한 입력 → 계산 → 결과 설명과 실행 근거·미검증 범위를 같은 PR에 담는다.
- [ ] 실제 내부 유즈케이스를 통해 결과를 확인한다. HTTP 조회 API나 #58의 재개 판단 연결 없이 이번 대조 범위를 검증한다.

**제외:** HTTP 조회 API, 돈 자동 보정/재생성, 주문장 복원, 기존 DB 자동 이행/삭제, 주기적 감시, 다중 서버/다중 마켓의 hold 소유 체계, #58의 마켓 차단·재개 연결, #67~70의 프로세스 강제 종료 테스트, #50의 주문 입력 저장.

**일치가 증명하지 않는 것:** 모든 기록과 잔고가 함께 지워졌다면 외부 증거 없이 복원할 수 없다. 서로 상쇄되는 잘못된 기록은 합계만으로 모두 찾아낼 수 없다. 반환 원장·예약의 정확한 사건별 대조는 기존 #73 등의 계약을 재사용한다. 검사기는 전체 거래 감사를 대신하지 않는다.

특히 취소 이벤트·주문장 변경이 완료된 뒤 자금 반환이 실패하면, 돈의 DB 트랜잭션은 롤백돼 원장·잔고·활성 예약끼리는 일치할 수 있다. **이때도 주문 처리 전체가 정상이라는 뜻은 아니며 기존 마켓 실패 차단을 해제하지 않는다.** 복구 진행 상태와 함께 재개를 판단하는 것은 #58의 책임이다.
