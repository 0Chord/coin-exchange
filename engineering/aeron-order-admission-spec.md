## 이번에 무엇을 만드는가

**Aeron으로 받은 주문을 이미 있는 접수 함수에 연결한다. 준비한 돈을 주문에 묶고, 접수 승인 또는 거절을 돌려준다.**

앞 단계인 #97은 “사용자 A에게 테스트용 1,000 USDT를 준비해 달라”는 요청까지 연결했다. #98은 같은 노드·같은 메모리 잔고에 “100 USDT 가격으로 BTC 3개를 사겠다”는 주문을 보낸다. 돈 계산·재전송 판단은 기존 코어를 쓰고, 이번에 더하는 기능은 **주문 메시지와 그 코어를 실제 통신으로 연결하는 것 하나**다.

| 사용자 A의 USDT | 사용 가능 | 주문에 묶인 돈 |
| --- | ---: | ---: |
| 자금 준비 직후 | 1,000 USDT | 0 USDT |
| 300 USDT가 필요한 주문 R1 승인 후 | 700 USDT | 300 USDT |
| 같은 R1을 다시 보낸 후 | 700 USDT | 300 USDT |

노드에는 승인 순번 1·대기 주문 1건·주문별 예약 1건·RESERVE 원장 거래 1건이 남는다. RESERVE 거래에는 **사용 가능 금액에서 300 감소 / 예약 금액에 300 증가**를 나타내는 두 분개가 있다. 처음 자금을 준비한 OPENING 거래도 유지한다.

**접수 승인은 체결 완료가 아니다.** 이번에는 주문장에 넣어 매칭하거나 정산하지 않는다.

## 두 거절은 왜 재전송 결과가 다른가

| 거절 | 이미 판단한 내용 | 같은 요청을 다시 보내면 |
| --- | --- | --- |
| 잔고 부족 | 엔진이 당시 돈으로 접수 가능 여부를 판단했다. 최초 거절과 당시 부족 금액을 기억한다. | 나중에 돈이 생겨도 최초 거절을 돌려준다. 다시 판단받으려면 새 요청 ID를 쓴다. |
| 노드 설정과 불일치 | 보낸 마켓·수수료 정보가 이번 개발 노드의 고정 설정과 다르다. 접수 판단에 넘기지 않았다. | 설정을 바로잡으면 같은 요청 ID로 처음 판단받을 수 있다. |

예를 들어 **돈이 0일 때 R2를 보내 거절 → 1,000 USDT 준비 → 같은 R2 재전송**이면 여전히 당시의 부족 거절이다. 반면 **처음 보내는 R3의 수수료 정보가 잘못됨 → 올바르게 고쳐 R3 재전송**이면 그때 접수 여부를 판단한다.

여기서 “기록하지 않는다”는 **코어의 최초 요청 이력·예약·금전 원장을 만들지 않는다**는 뜻이다. 설정 불일치 메시지도 Aeron 입력 로그에 남을 수 있다.

## 요청이 지나가는 길

**개발 클라이언트 → Protobuf 주문 바이트 → Aeron → 기존 노드의 주문 분기 → 기존 접수 함수 → 작은 승인·거절 응답**

클라이언트는 같은 저장소에서 실행하는 개발용 프로그램이다. 새 웹 서비스가 아니다. 노드는 #97에서 실행한 것을 그대로 사용한다. 아래 상세 항목은 구현과 검증 때 필요한 부분만 펼쳐 읽는다.

### 이번 실행에서 고정할 값

| 항목 | 첫 시연 값 |
| --- | --- |
| 마켓 정의 | BTC-USDT / 기준 자산 BTC / 표시 자산 USDT / BTC scale 8 |
| 수수료 정책 | SPOT / NORMAL / scheduleVersion 1 / maker 0ppm / taker 0ppm |
| 금액 표시 | 1 USDT = 1,000,000 최소 단위, 1 BTC = 100,000,000 수량 단위 |
| BUY 시연 입력 | 가격 100,000,000·수량 300,000,000 → 100 USDT × 3 BTC → 예약 300 USDT |

이 값들은 개발 예시다. 실제 거래소의 가격·수량 간격 정책을 약속하지 않는다. 노드가 시작할 때 유효한 불변 설정으로 준비하고 한 실행 동안 바꾸지 않는다. 동적 정책 관리·사용자별 수수료 정책 조회·DB 조회는 만들지 않는다. 잘못된 노드 설정은 기동 실패이며, 잘못된 요청 설정은 아래의 접수 전 거절이다.

수수료가 0이 아닌 유효한 설정을 테스트에서 명시했을 때도 기존 예약 계산기를 사용한다. BUY의 최대 요율 예약·반올림과 SELL의 기준 자산 예약 규칙을 새로 만들거나 바꾸지 않는다.

### 모든 주문의 처리 순서

1. callback의 정확한 offset·length 구간을 크기 제한 후 복사하고, 기존 프레임·Protobuf·필수 값 검증을 통과시킨다. 손상 메시지는 여기서 끝낸다.
2. 같은 상태 객체가 사용 가능한지 확인하고 (userId, requestId)가 이미 처리된 키인지 확인한다. 차단 검사가 이 조회보다 먼저다.
3. **기존 키이면 기존 admit에 그대로 넘긴다.** 코어의 식별자 검사·원본 비교 순서를 유지한다. 유효한 같은 원본이면 최초 결과, 유효한 다른 원본이면 REQUEST_CONTENT_CONFLICT다. 새 설정과 비교해 최초 결과를 가로채지 않는다.
4. **신규 키만 고정 설정과 비교한다.** 주문 원본의 marketId와 마켓 정의의 네 값, 수수료 정책의 상품·등급·버전·maker/taker 값을 모두 대조한다. 정의만 같고 주문 marketId가 다른 경우도 사유 9다.
5. 신규 설정 불일치는 사유 9로 반환한다. 코어 admit을 호출하지 않고 최초 요청 이력·돈·원장·대기·승인 순번을 바꾸지 않는다.
6. 설정이 맞으면 기존 admit을 호출한다. LIMIT+GTC 승인 또는 기존 정상 거절을 작은 응답으로 보낸다.

형식 오류는 위 모든 업무 분기보다 우선한다. 기존 키는 코어의 식별자 검사 순서를 그대로 따른다. 신규 키에서 식별자 업무 오류와 설정 불일치가 함께 있으면 설정 불일치가 먼저이며, 설정이 맞은 뒤의 식별자·조건 거절은 코어가 판단한다.

**원본**은 OrderAdmissionInput의 사용자·마켓·주문 ID·매수/매도·주문 조건·가격·수량이다. 같은 요청에 전달한 마켓 정의·수수료·원장 ID·업무 시각은 최초 판단의 문맥이며 원본과 구분한다. 읽을 수 있는 문맥을 바꾼 재전송도 기존 결과를 먼저 사용한다. 손상되거나 표현할 수 없는 문맥은 기존 코덱에서 거절한다.

조회와 접수는 같은 callback 실행자가 연속 수행한다. 별도 스레드가 그 사이 상태를 바꾸지 않는다. 어댑터에 두 번째 요청 이력 맵을 만들지 않는다. [Aeron 업무 코드 지침](https://aeron.io/docs/aeron-cluster/efficient-business-logic/)의 결정론·업무 I/O 분리 원칙을 유지한다.

<summary>3. 승인 응답과 전송 형식</summary>

승인은 기존처럼 사용자·요청·마켓·주문 식별자와 **승인 순번**만 담는다. 현재 잔고·주문별 예약·후보·원장 전체는 응답에 넣지 않는다. 테스트에서는 노드가 공개한 완성된 상태 사본을 별도로 읽어 금액과 기록을 대조한다.

- 기존 8바이트 헤더·schema 87/version 2·필드 번호와 메시지 종류 1~6을 유지한다.
- 기존 RejectionReason 1~8의 숫자를 유지하고 **EXECUTION_CONTEXT_MISMATCH=9** 하나를 추가한다. 다른 형식·일반 오류 응답은 추가하지 않는다.
- app-api의 응답 사유 표현에서 도메인 1~8과 전송 전용 9를 명시적으로 매핑한다. enum 이름의 우연한 일치나 ordinal에 의존하지 않는다.
- 순수 OrderAdmissionResult.Reason에는 9를 넣지 않는다. 설정 오류를 코어가 최초 업무 거절로 보관하지 않는다.
- 부족 상세는 INSUFFICIENT_BALANCE에만 필수다. 9 또는 다른 사유에 붙으면 변환 오류다.
- 미지원 사유·누락·길이·잘린 바이트·UTF-8·식별자 경계에 대한 기존 검증은 유지한다.

Protobuf에 enum 값을 추가할 수 있다는 것과 **우리 구버전 코덱이 새 사유를 지원한다는 것**은 다르다. 기존 코덱은 9를 지원하지 않는다. 이번 개발 클라이언트와 노드는 같은 #98 지원 버전으로 사용한다. 기존 고정 메시지를 새 코덱이 읽는 회귀, 새 사유를 기존 검증 경계가 거절하는 사례, 새 사유 왕복을 대조한다. 구 코덱 확인에 별도 구버전 런타임·범용 호환성 프레임워크를 만들지 않고 검토 가능한 기존 검증 코드나 작은 고정 fixture를 사용한다. [Protobuf 변경 규칙](https://protobuf.dev/programming-guides/proto3/#updating)에 따라 기존 필드 번호를 재사용하지 않는다. 실제 혼합 배포 보장은 후속이다.

클라이언트는 응답 종류와 사용자·요청·마켓·주문 식별자를 현재 대기 중인 주문과 대조한다. 승인 순번은 양수여야 한다. 다른 요청·자금 준비 응답·손상 응답을 주문 성공으로 표시하지 않는다. 한 번에 하나의 요청을 기다리고, 기존 고정 egress 포트를 고려해 개발 클라이언트들을 순차 실행한다.
